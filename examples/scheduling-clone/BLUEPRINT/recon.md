## 3 全部入口清单

| 入口 | 类型 | 地址/路径 | 说明 |
|---|---|---|---|
| 主理人主页 | URL | `/<hostSlug>` | 公开页，列出该主理人的预约类型 |

## 4 核心用户流程

| ID | 流程 | 屏幕序列 | 步数 |

| FL-01 | 访客预约一个时段 | S-03 → S-04 → S-05 | 5 |

```
预约页 S-03 ──依赖──> 可用规则 E02 ──依赖──> 预约类型 E01
     │                     │
```

**无循环依赖。** 关键单向：`E01 → E02 → E03 → E05`。E03 依赖 E01 与 E02 的配置来校验时段。

## 6 数据模型概览

| 实体 | 一句话 | 明细 |
|---|---|---|
| E01 EventType 预约类型 | 时长、缓冲、提前通知、时区、问题 | `data-dictionary.md` |
| E02 Availability 可用规则 | 每周哪几天、什么时段可约 | 同上 |
| E03 Booking 预约 | 谁在什么时间约了什么 | 同上 |
| E04 Host 主理人 | 谁在提供服务 | 同上 |
| E05 Reminder 提醒 | 什么时候提醒谁 | 同上 |
| E06 Outbox 发件箱 | 要发的通知（与业务同事务落库） | 同上 |

**取证的发现**：原版把"可用规则"存成每周重复的 RRULE 字符串（形如 `FREQ=WEEKLY;BYDAY=MO,WE,FR`）。**这是最值得学的设计**——用标准格式表达重复规则，避免自己造轮子。本地映射为 `E02` 的 `(weekday, startMin, endMin)` 行式存储，理由是查询要用 SQL 下推（`availability` 表可直接 JOIN 过滤），而 RRULE 字符串必须展开成行才能高效查询。

## 7 可见区域与不可见区域

**能看到**：公开主页、预约页、表单、成功页、改期页、帮助中心、公开定价页、应用商店/官网截图、公开演示视频。

**看不到（必须明确写出，不能装作已知）**：
- 服务端实现（用了什么数据库、什么框架）
- 支付后的完整能力（免费档看不到）
- 团队功能（多人协作、负载分配）
- 集成市场（日历、CRM、视频会议）
- 移动端原生行为（只有响应式 Web）
- 运营后台与风控

**这一节的作用**：防止把"我没看到的"当成"原版没有的"，也防止把付费墙当功能缺失去复刻。

## 10 规模判断与建议

| 维度 | 数 |
|---|---|
| 屏幕 | 10 |
| 流程 | 5 |
| 实体 | 6 |
| 端点（推断） | 约 15–25 |

**难点排序**（先验最难的）：
1. **时区与夏令时**（槽位生成、跨日界、DST 空档）—— 最容易出错且最难测
2. **并发抢时段**（防超卖必须在数据库层）
3. **提醒的一致性**（改期要同事务取消旧提醒 + 建新提醒）
4. **重复提交幂等**

**规模**：**M**（几周）。比"完整克隆"小，因为本项目砍掉了团队、市场、集成、支付。

**建议**：先做 FL-01 的竖切（能约上就是胜利），再做主理人侧设置，最后做提醒。
