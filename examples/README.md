# 完整样板：预约调度网站

> 一个跑完 **S0 → S2** 的真实颗粒度样板。目的：让你在开工前就知道「细节级产出」到底长什么样，而不是读一堆原则。
>
> 选这个例子的原因：你举的例子就是它；而且它同时具备三个难处——**时区、并发抢时段、跨页面联动**，最能暴露"框架有、细节没想透"。

---

## 这个样板有什么

```
examples/scheduling-clone/
├── BLUEPRINT/
│   ├── recon.md            逆向地图（10 段，Web 版如何在无 SHA-256 时替代）
│   ├── features.csv        16 个功能（含 3 个 skip 及理由、2 个差异化）
│   ├── menus.csv           18 个菜单节点，三条件分离，含 4 层嵌套
│   ├── screens.csv         10 个屏幕，五态齐
│   ├── flows.md            3 条流程展开（正常/失败与取消/边界/恢复 四段齐）
│   ├── linkage.csv         44 条联动，六面全覆盖
│   ├── unknowns.csv        10 条未知（4 条阻断级仍 open）
│   ├── state-machines.md   3 个状态机（页面加载/预约单/提醒）
│   ├── data-dictionary.md  6 个实体 + 全局时间口径章 + 双写字段决策
│   └── contracts/
│       └── C-F-BOOK-PAGE.md    ★ 完整 16 节契约，448 行
└── _gen_*.py               4 个生成脚本（保证 CSV 引用与顺序不出错）
```

**只有一份完整契约是刻意的**：写 16 份稀释质量的样板没有意义。一份够细的，能让你判断"我们能不能做到这个颗粒度"。

**这个样板处于「诚实的中途状态」**：
- 13 个 must 功能**只有 1 个写了契约** → 门禁会报 `contract-coverage` FAIL
- 4 条阻断级未知仍 `open` → G3 会拦
- 联动矩阵显示 48 格"无条目" → 提醒你还有多少面没想过

**这是刻意的教学态**：它同时演示"结构齐了"和"细节还没写完"，而门禁能准确指出差多少。**一份全绿的样板反而看不出门禁的作用。**

**拿它当门禁的冒烟用例**：改坏一处（比如把某个 radio 的 `checked_cond` 清空、把某条 linkage 的 `status` 从 `wired` 改成 `pending`），门禁必须立刻报 FAIL。

## 三个可以直接看的东西

### 1. `features.csv` —— 十六行，看清"功能索引"该长什么样

```csv
F-FLAT-PRICING,按团队而非按人头计价,定价页,must,in,no,no,contracts/C-F-PRICING.md,T-601,recon.md#x-11,差异化：原版按人头涨价被骂
F-TEAM-ROUNDROBIN,团队轮流分配,分配,should,out,yes,skip,-,-,recon.md#x-12,A档第一版不做：需要多主理人与负载模型
```

两个关键点：
- `original=no` 表示**原版没有、你新增的**——不计入一致性分数，单独列出。
- `scope=out` + `progress=skip` + 理由——**"不做"是合法的，但必须写明理由**，否则 S9 评分时会被误算成缺失。

### 2. `menus.csv` —— 看三条件怎么分离

摘一段（时区菜单，4 层）：

| 节点 | visibility_cond | enabled_cond | checked_cond |
|---|---|---|---|
| 时区 › 手动选择 | 始终显示 | 始终可用 | `tz.mode == 'manual'` |
| 时区 › 手动选择 › 搜索框 | `tz.mode == 'manual'` | 输入非空才触发筛选 | `tz.query` 非空 |
| 时区 › 手动选择 › 列表 | `tz.mode == 'manual'` | 列表非空时可用 | `tz.selected == 该项` |

再看一个**可见但禁用**的真实场景：

| 节点 | enabled_cond |
|---|---|
| 预约类型 › 删除 | 该类型下无未来预约；否则禁用并提示"还有 3 个未来预约" |

注意：**禁用解释必须给出具体数字**，不能只说"不能删"。

### 3. `C-F-BOOK-PAGE.md` —— 448 行，一份契约该有多细

随便看几段，感受颗粒度：

**§6 筛选条件**给出**规则求值顺序**（顺序错结果就不同）：
```
1 展开可用规则 → 2 减已存在预约 → 3 减缓冲 → 4 减最小提前通知
→ 5 减预约窗口上限 → 6 按时长切分 → 7 套访客时区（只在渲染层）
```

**§6 边界表**逐条列出易错点，例如：
> 时段恰好等于 `now + minNotice` → **可选**（用 `>=` 不是 `>`）

**§12 跨页面联动**明确区分两个"看起来一样"的口径：
> 日期格角标 = 该日剩余时段数；侧栏角标 = `status=confirmed` 的预约数。**两者口径不同，必须分别定义。**

**§15 体验标准**每条都可判定：
> 输入法组合：搜索框内组合输入期间**不触发**筛选；`compositionend` 后才筛选。判据：用中文输入法打"上海"，过程中网格不闪。

**§16 测试**每条断言对具体值：
> T-101：网格渲染出 5 个时段，首个 `14:30`，最后一个 `16:30`；角标「5」

## 这个样板示范的三个"必须想透"的地方

### 时区：三个不同的东西容易被混成一个

| 概念 | 是什么 | 搞错的后果 |
|---|---|---|
| **绝对时刻** | `startAt`（UTC 时间戳） | 切时区时被"重算"→ 实际时间变了 |
| **钟面时间** | 访客看到的 `15:00` | 存成字符串 → 夏令时切换日错一小时 |
| **时区标识** | `Asia/Shanghai` | 只存 GMT 偏移 → 夏令时切换后偏移过期 |

正确做法：**业务数据存绝对时刻 + 时区标识；钟面时间只在渲染层计算**。

对应契约里的具体条目：
- §6 边界表："夏令时切换日该日真实时长可能是 23h 或 25h；时段按本地钟面时间切分，**跳过不存在的钟面时刻**"
- §10 派生值："`isPast` 一律以服务端时间为准"
- T-108："美东 3 月第二个周日该日只有 23 小时；不出现不存在的钟面时刻（02:00–03:00）"

### 并发抢时段：这是数据库问题，不是 UI 问题

样板里 `linkage` 的 LK-014 与 T-109 明确：

> 提交时必须**重新校验** `selectedSlot` 仍可用；校验失败返回 `SLOT_TAKEN`，前端进入 `CONFLICT`；**保留表单已填内容**。

数据库层面对应（`SPEC/schema.sql` 该有的写法）：

```sql
-- 两个访客不可能订到同一时段：用排除约束，不是靠 UI 灰掉
alter table bookings
  add constraint no_overlapping_bookings
  exclude using gist (host_id with =, tstzrange(start_at, end_at) with &&)
  where (status <> 'cancelled');
```

**为什么不能用"UI 灰掉"实现**：两个标签页、两台设备、慢网络下都会绕过。

### 六面联动：六面里的"提醒"最容易被漏

完成/改期/取消一个预约，**都要动提醒**。样板里三条联动专门管这个：

| 联动 | 场景 | 为什么容易漏 |
|---|---|---|
| LK-014 | 新建预约 → 登记 24h 前提醒 | 容易只写 booking 不写 reminder |
| LK-018 | 改期 → **取消旧提醒 + 登记新提醒，同一事务** | 不同事务会出现"改了但还提醒旧时间" |
| LK-023 | 取消 → 取消全部待触发提醒 | 漏了会骚扰用户，且功能"看起来"正常 |

**"同一事务"这四个字是这一条的全部价值。** 只写"改期时要更新提醒"是不够的——分成两次写就意味着中间可能失败。

## 怎么用这个样板

**开工新项目时**：不要复制它的业务字段，只复制**结构**——打开 `C-F-BOOK-PAGE.md`，看着它的颗粒度写你自己的契约。写不出来这么细，说明还没拆透。

**评审时**：把开发者写的契约和这份并排看，如果明显更粗，打回。

**跑门时**：这份样板的 `features.csv` / `menus.csv` / `linkage.csv` 可以直接作为 `gates/fixtures/` 的素材，用来验证门禁能识别"缺少契约""未 wired""条件写'按原版'"。

## 跑一遍看看门禁说什么

```bash
cd 经验萃取

# 1) 蓝图自检（细节层）
python3 tools/blueprint_lint.py --project examples/scheduling-clone
#   → 会告诉你：12 个功能缺契约、哪个 CSV 列不对、哪个引用断了

# 2) 菜单穷举（只看三条件齐不齐）
python3 tools/menu_walk.py --project examples/scheduling-clone --gaps
#   → 缺项表：每个叶子有没有 command / contract_ref / 三条件

# 3) 联动矩阵（你最关心的那个）
python3 tools/linkage_matrix.py --project examples/scheduling-clone
#   → 功能 × 六面矩阵，标出每面 wire / pending / na / 无条目

# 4) 门禁（阶段级）
python3 gates/run.py --project examples/scheduling-clone --stage G2
#   → 逐条：期望 / 实际 / 证据路径 / 修复动作
```

**第 3 步是最值得看的一个**。它的输出直接回答"页面做出来了，内部联动到底做了几面"。

## 这份样板哪里还不足（诚实）

| 不足 | 原因 | 你要补的 |
|---|---|---|
| 12 个 must 功能没有契约 | 写 12 份会稀释质量 | 按同一颗粒度自己写 |
| 没有 `SPEC/`（架构/表/路由） | 那属于 S4 | 跑 S4 阶段卡 |
| 没有真实截图证据 | 这是设计样板，不是已完成的取证 | 真项目必须有截图 |
| 没有 `BLUEPRINT-LOCK.md` | 那是 S3 冻结时才生成的 | 走完 S3 |
| 时区规则只写了 A 档支持范围 | 跨午夜窗口等明确 out-of-scope | 你的项目若需要，先补 unknown 再扩契约 |
| 4 条阻断级未知仍 open | 刻意的 | 补验后关闭，否则 G3 不放行 |
