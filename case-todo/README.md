## 3. 这一次的三个真实事故（全部与数据丢失有关）

| # | 事故 | 现象 | 真因 | 修法 |
|---|---|---|---|---|
| 1 | fire-and-forget 落库 | 改完立即关窗，数据丢；空载时约 3%，间歇性 | `_ = SaveAsync()` 不等待，写不进串行链 | 引入 `_pendingSave` 串行链 + 可 await 的 `PendingSave` |
| 2 | 防抖 Timer 逃逸 | 改标题后不失焦直接 Cmd+Q，**100% 丢** | 300ms 防抖 Timer 回调直接调用仓储，不在写链内 | 防抖到点也必须 `EnqueueSave` |
| 3 | 关窗无冲刷 | 测试里手工 Flush 全过，真实 UI 关窗仍丢 | 只有测试代码调了 Flush，产品代码没有 `Closing` 拦截 | `Closing` 拦截 → `e.Cancel=true` → Flush → await PendingSave → `Dispatcher.Post(Close)` |

**最值钱的一课**：事故 1 和 2 的早期测试**全都是绿的**，因为测试里用了 `Task.Delay(...)` 等一会儿再断言——**恰好把竞态伪装成了通过**。这就是 R1 的来源，也是"测试全绿不可信"的实证。

**第二课（AUD-01/02）**：修好之后，测试里出现了 `Assert.True(dataSaved || hasClosingFlush)` 这种**或放行**——数据已丢，只要代码里出现 Flush 字样仍然绿。这是 R19 的来源。

## 4. 这一次踩过的取证坑（详见 `失败模式库.md`）

| 坑 | 一句话 |
|---|---|
| arm64 chained fixup 掩码 | 应为 **48 位**（`& 0x0000FFFFFFFFFFFF`），用 51 位会读出空串/半截选择器 |
| Swift 类布局 | `class_ro_t` 不通用，`data` 指针低 3 位带 tag；权威来源用 `otool -oV` |
| 静态找到方法 ≠ 有调用点 | 某 50 方法的类 `__objc_selrefs` 调用点为 0，是死代码；静态结论必须补调用点证明 |
| Swift 静态派发 | 内部调用绕过 `objc_msgSend`，只看 ObjC 派发会得出错误结论 |
| 动了原程序就变空壳 | 签名与权限链一旦破坏，应用组数据就读不到 → **只读不改是红线** |
| 在原库上写会被覆盖 | 外部写入被程序下次落盘覆盖 → **只在副本上只读导出** |
| `.NET` 元数据损坏 | 10 张表从未提取出列定义；1,163 方法空壳 |
