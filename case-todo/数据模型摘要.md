**重要更正**：旧文档多处写「7 张表类型名在元数据中损坏，故记 75」。实测是 **10 张表没有列定义**（68 − 58 = 10），且这 10 张不是"损坏"，是**从未被提取**（见 §2 清单）。所以"75 表"这个口径应当作废——它不是另一种数法，是错误推断。

**这条更正本身就是体系的教训**：一个数字被抄进三份文档后，就没人再算它了。所以 v2 的门禁要求**数字必须配复算命令**，`case-todo/README.md` 的事实基线表也按此改写。

## 2. 无列定义的 10 张表

```

**为什么重要**：这 10 张表覆盖了「番茄钟 / 专注 / 便签 / 计时器」四个功能域。也就是说——**这四个功能域的数据结构完全未知**。

U-010,番茄钟,10 张表无列定义,番茄/专注/便签/计时四域无法建模,缺 .NET 类型元数据,从损坏的 DLL 重跑 ILSpy 或用其余 58 表反推,规划,yes,open

## 3. 核心实体：`TaskModel`（63 字段）

这是整个应用的重心。按语义分组看：

### 3.1 身份与归属
```
id            string   主键
userId        string   归属用户
projectId     string   所属清单
parentId      string   父任务（子任务树）
columnId      string   看板列
creator       string
assignee      string   指派给谁
```

### 3.2 时间（最容易出错的部分）
```
dueDate         DateTime?   截止
startDate       DateTime?   开始
remindTime      DateTime?   提醒时刻
completedTime   DateTime?   完成时刻
createdTime     DateTime?
modifiedTime    DateTime?
repeatFirstDate DateTime?   重复首次发生
timeZone        string      时区
isFloating      bool?       浮动时间（不带时区）
isAllDay        bool?       全天
pinnedTime      string      置顶
pinnedTimeStamp long
ParseTz         bool        解析时区
```

**必须明确的三件事**（不明确就一定做错）：
1. `dueDate` 是「本地日期」还是「UTC 时刻」？—— 有 `timeZone` + `isFloating` 字段，说明**两者都可能**。
2. `isAllDay=true` 时 `dueDate` 的时分秒是否有意义？—— 无意义，但可能被写成 `00:00:00` 或 `23:59:59`，两种都会造成"跨天"错误。
3. `isFloating=true` 是否意味着跨时区旅行时保持钟面时间不变？—— 这是 `isFloating` 存在的唯一理由。

这三条都必须进 `unknowns.csv`，用真实操作验证，**不许凭字段名猜**。

### 3.3 重复
```
repeatFlag     string    重复规则（iCal RRULE 风格字符串）
repeatTaskId   string    重复任务的主任务 ID
repeatFrom     string    从哪一侧修改（THIS / FUTURE / ALL 之类）
exDate         string[]  排除日期
exDates        string    排除日期（序列化形式）
```

**注意 `repeatFlag` 是字符串**——意味着规则解析在应用层，不是数据库层。这正是原版那 1,647 行重复规则算法的位置。

**`exDate` 与 `exDates` 并存**（一个数组一个字符串）——**典型的历史遗留双写**。重建时必须选一个作为权威，另一个只在读取旧数据时兼容。

### 3.4 提醒
```
reminder   string              提醒规则（序列化）
reminders  TaskReminderModel[] 提醒列表（子表）
```

`TaskReminderModel` 只有 4 个字段：`id / Taskid / taskserverid / trigger`。`trigger` 是字符串——同样是应用层解析。

**这里有 X-01 的典型场景**：改 `dueDate` 后，`reminder` / `reminders` / `remindTime` 三者都要重算，且 `SettingsModel.AllDayCustomRemind` / `TimeCustomRemind` 是默认提醒配置，也要参与。**六个面联动里"提醒"这一面，实际牵动 5 个字段 + 1 张子表 + 2 个设置项。**

### 3.5 状态与删除
```
deleted       int      0 正常 / 1 垃圾箱 / 2 永久删除
status        int
isCompleted   bool
progress      int?     完成百分比
completedUserId string
```

**三态删除**（0/1/2）是原版的设计，重建时必须照做——因为"垃圾箱"是一个独立的智能清单，`deleted=1` 的行要出现在那里，`deleted=2` 的行不出现在任何地方。**如果只做软删除（bool），垃圾箱就实现不了。**

这也解释了为什么 `SmartListTrash` 是 `SettingsModel` 的一个字段——侧栏"垃圾箱"的计数。

### 3.6 内容与标签
```
title     string
content   string    正文
desc      string    描述（与 content 并存？—— 又一个待验项）
tag       string    标签（序列化）
tags      string[]  标签数组
label     string
kind      string    任务类型
Color     string
sortOrder long
```

**`content` 与 `desc` 并存，`tag` 与 `tags` 并存**——又是双写。**每个"并存"都是一次历史迁移的残留，重建时都必须选一个权威**。

## 4. 侧栏「智能清单」的实现线索

`SettingsModel` 里有：
```
SmartListAll / SmartListToday / SmartListTomorrow / SmartList7Day
SmartListForMe / SmartListComplete / SmartListAbandoned / SmartListTrash
SmartListTag / SmartListInbox / SmartListSummary
```
以及 `SortOrderOfAll / Today / Tomorrow / Week / Calendar / Inbox / Tag / Event / Assign`

**结论**：智能清单不是表，是**配置驱动的查询**——每个清单的显示开关、排序方式、顺序都存在 Settings 表里。

**这直接影响重建方案**：不要为"今天/明天/最近7天"建表，它们都是 `TaskModel` 上的查询条件。建表会导致 X-01（联动不同步）——因为同一个任务会同时属于多个清单。

**对应联动条目**（`linkage.csv`）：
```csv
LK-001,F-TASK-COMPLETE,TaskCompleted{taskId},S-01,主列表该行移入"已完成"分组,,提交成功后,保留选中;若"隐藏已完成"开启则整行移出并聚焦下一行,T-110,wired
LK-002,F-TASK-COMPLETE,TaskCompleted{taskId},S-01,侧栏「今天」角标重算,COUNT(dueDate=今天 AND isCompleted=0),事件广播后,不清空, T-110,wired
LK-003,F-TASK-COMPLETE,TaskCompleted{taskId},S-01,侧栏「已完成」角标 +1,同上,事件广播后,不清空,T-110,wired
LK-004,F-TASK-COMPLETE,TaskCompleted{taskId},S-03,日历视图中该条变灰/加删除线,TaskModel.isCompleted,提交成功后,不清空,T-111,wired
LK-005,F-TASK-COMPLETE,TaskCompleted{taskId},S-04,搜索结果该条标注已完成,TaskModel.isCompleted,下次搜索（不需实时）,保持当前结果集,T-112,wired
LK-006,F-TASK-COMPLETE,TaskCompleted{taskId},S-02,详情面板复选框打钩 + 保存状态,TaskModel.isCompleted,乐观更新后由写入结果确认,保留焦点在复选框,T-113,wired
LK-007,F-TASK-COMPLETE,TaskCompleted{taskId},-（提醒调度）,取消该任务的待触发提醒,TaskModel.reminders,提交成功后重算,不清空,T-114,wired
```

**看 LK-007**：完成一个任务要取消它的提醒。**这一条如果漏了，用户会被已完成任务的提醒打扰**，而且测试很难发现——因为功能"看起来"是好的。这就是为什么六面联动必须逐条列、逐条测。

## 5. 限额与账号档位：采证时必须记录的一件事

原版里很多"限制"不是产品设计，而是**账号档位**带来的。在付费档账号下采证，看到的是"无限"；换到免费档用户那里，同一个功能就有数量上限（项目数、附件大小、提醒条数、看板数……）。

**这直接影响你对"原版行为"的理解**：把付费墙当成功能缺失来复刻，你会白做一堆本来不存在的限制；反过来，把付费墙当成产品设计，你会把一个商业边界抄进自己的产品。

**判定**：
- `features.csv` 里与限额相关的功能一律 `scope=out` + `progress=skip` + 理由「A 档自用，不做付费体系」
- `recon.md` 第 7 段必须写「采证时的账号档位」
- `unknowns.csv` 留一条：还有哪些行为可能被我当时的账号档位掩盖了

这是 S1 的通用要求，与具体产品无关。

## 6. 给重建的三条结论

1. **建 20 张核心表就够启动**：Task / Project / Tag / TaskReminder / Settings / ProjectGroup / Section / Filter / Countdown / 再加同步相关（A 档可删）。本地版实测建表 234 ms / 20 张。剩下的按功能模块逐步加，避免启动变慢。
2. **删同步字段**：`etag / syncStatus / SyncPoint / LastCheckSyncDate / needPullRemote / SyncTimelineModel` 等在 A 档全部无意义。但**删之前要在数据字典里记一笔**，并确认没有业务逻辑依赖它们（比如排序可能用了 `sortOrder`，而 `sortOrder` 在同步场景才有跨设备意义）。
3. **每个"双写字段"选一个权威**：`exDate`/`exDates`、`content`/`desc`、`tag`/`tags`。选完写进 `data-dictionary.md` 的「本地映射」列。不选就一定在两个地方各写一遍，然后不一致。

## 7. 这个案例在体系里的位置

本文件是 **S1 产出的一部分**（`data-dictionary.md` 的上游），不是规范。它的价值在于：

- 证明"字段即需求"：63 个字段背后是 63 条业务规则
- 证明"字段名不等于语义"：`isFloating` / `ParseTz` / `desc` vs `content` 都需要实测
- 证明"历史遗留双写"是常态：三个并存字段组
- 证明"数字必须有复算命令"：连"7 张表损坏"这种看着很具体的说法，实测都是错的（实际 10 张表无列定义）
