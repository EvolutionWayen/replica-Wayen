## X-01 功能清单齐，做出来内部不联动

**症状**：每个页面单独看都对，但改完 A 页面，B 页面不更新；角标数字不变；日历上不移动；搜索还是旧结果；提醒不重排。

**真因**：需求只列了"有哪些功能"，没列"功能之间怎么互相影响"。开发时每个功能各自实现，写完各自的界面就以为完了。

**证据**：目标应用实操中，改日期后需要同步影响 **6 个面**——主列表行、侧栏「今天/明天」角标、任务详情、日历视图、搜索结果、提醒调度。v1 的功能清单（`docs/17-功能对照表.md`）只有一列"状态"，没有任何"联动"列，导致这 6 个面里有几个是后来才发现漏掉的。

**现在由什么挡住**：
- `BLUEPRINT/linkage.csv` 强制记录每一行：源事件 → 受影响控件 → 刷新时点 → 保持不变的状态 → 测试号
- **G6 联动门**：功能标 `progress=yes` 时，其所有 linkage 行必须 `wired`/`verified` 且有通过的测试；完全没有 linkage 行直接 FAIL
- `tools/linkage_matrix.py` 输出六面矩阵；只有 1 面的功能被标为「可疑」

**正确写法**：
```
不许写：日期改了要刷新界面
必须写：TaskDateChanged 提交成功 → (1) 主列表该行日期徽标就地更新，不重排整表
       (2) 侧栏「今天」「本周」角标重算并就地更新
       (3) 详情面板日期字段显示新值，保留焦点在日期按钮
       (4) 日历视图该任务落到新日期，跨周时重排
       (5) 搜索结果按新日期重新过滤该条
       (6) 提醒调度器重算下次触发时刻
       测试：T-103 改日期后六面断言；T-104 在"今天"筛选下改成明天 → 该行移出列表且焦点落到下一行
```

## X-02 多层菜单做出来选项不对、该灰的不灰

**症状**：菜单层级画对了，但选项出现时机不对（该隐藏的显示）、可用性不对（该禁用的可点）、选中态不对（点了没打钩 / 打钩了但点了不生效）。

**真因**：把「显示条件」「可用条件」「选中条件」混成一句"看情况"。这三件事是三种完全不同的判断：

| 判断 | 决定什么 | 错误后果 |
|---|---|---|
| 显示条件 | 节点在不在 | 显示了不该有的选项，用户误以为支持 |
| 可用条件 | 能不能点 | 该灰的能点 → 点了报错或静默无效 |
| 选中条件 | 打不打钩 | 打钩错位 → 用户以为设置成功，实际没改 |

**证据**：日期菜单里 `清除日期` 只在"已有日期"时可用，但在"仅重复无日期"的情况下仍然可见——这是典型的**可见但禁用**，需要单独一条 `enabled_cond`。重复菜单里「每周工作日」的打钩依据是 `repeat.byday` 是否覆盖周一至周五，而不是"用户上次点过它"——这是典型的**选中条件不等于点击历史**。

**现在由什么挡住**：
- `menus.csv` 三列强制分开：`visibility_cond` / `enabled_cond` / `checked_cond`
- **G2** 扫禁用词：出现 `按原版`/`视情况`/`同前`/`TBD`/`待定` 直接 FAIL
- `tools/menu_walk.py --cards` 逐叶子打印三条件卡，逼你一条条写

## X-03 边改边退，数据丢了

**症状**：改完立刻关窗，改动丢失；或者全部丢失（不是偶发）。

**真因**：三个独立缺陷，任何一个都足以丢数据：
1. **fire-and-forget**：`_ = SaveAsync()` 发出去没人等
2. **防抖 Timer 逃逸**：300ms 防抖回调直接调仓储，不在写入链内
3. **关窗无冲刷**：产品代码没有 `Closing` 拦截

**证据**：本次两次真实事故——空载时约 3% 丢（fire-and-forget，30 次丢 1 次）；改标题后不失焦直接 Cmd+Q **100% 丢**（防抖逃逸）。修法：`_pendingSave` 串行链 + `PendingSave` 可 await 信号 + 防抖回调也走 `EnqueueSave` + `Closing` 拦截。

**现在由什么挡住**：R2（串行链 + 完成信号）、R3（关窗冲刷 + 结构化结果）、G7（故障注入用例 + 退出冲刷证据 + 禁 `:memory:`）

**关键设计点**：冲刷必须返回**结构化结果**，不是 `Task` 完成就算：
```
FlushResult { status: ALL_COMMITTED | SOME_FAILED{detail} | TIMEOUT_UNKNOWN, pendingCount, failedIds }
```
否则"方法没抛异常"会被当成"保存成功"。

## X-04 测试全绿但用户一用就崩

**症状**：开发自测全过，用户第一次用就丢数据/崩溃。或者"单文件单跑全绿，整套跑偶尔挂"。

**真因**：测试用固定等待猜完成 + 用内存库测持久化 + 只跑单个测试文件。

**证据**：目标应用两起：① 早期测试全部 `await Task.Delay(800/1200)` 再断言 —— **恰好把竞态伪装成通过**；② 干净 HEAD 首次整套跑 `失败 1 / 通过 92`，错误 `no such table: TaskModel`，因为 `_ = InitAsync()` 是 fire-and-forget，1200ms 在冷启动不够；随后连跑 8 次全绿，单文件单跑 10 次全绿。③ 静态单例 `AppServices.Db` 导致跨测试串库，单文件绿、全量偶发失败。

**现在由什么挡住**：R1（禁固定等待）、R4（真文件 + 查具体值）、R5（连跑 ≥3 次）、G7（故障注入 + 重启读回）、G8（连续 N 次结果全 pass 才过）

**修法模板**：
```csharp
// 错误：await Task.Delay(1200); Assert.NotEmpty(await repo.GetAllAsync());
// 正确：
await vm.InitTask;                              // 暴露可 await 的初始化信号
await vm.PendingSave;                           // 可 await 的在途写
using var conn = OpenRealFileDb(tmpPath);       // 真文件
Assert.Equal("新标题", Scalar(conn, "SELECT title FROM TaskModel WHERE id=?", id));  // 查具体值
```

## X-05 改了 A 结果 B 被改

**症状**：编辑任务 A 后立刻切到 B，结果 B 被写成了 A 的内容；或者 A 的写入落到了 B 上。

**真因**：异步执行时才去读"当前选中对象"，而不是**入队时捕获**目标 ID。

**证据**：目标应用的 `TaskDetailViewModel` 里，lambda 在延迟执行时读取可变的 `TaskId`；`ClearDateAsync` 在 `:637-650` 清 `RemindTime` 后只排了一个保存，跨字段语义没进事务。

**现在由什么挡住**：契约 §11（数据写入）与 §13（并发与生命周期）强制要求「不可变命令」：`{operationId, entityId, patch, baseRevision, sequence}` —— `entityId` 在**入队时**捕获，执行时不许读当前选择。

**测试**：T-04「写 A 阻塞，立即切 B，再释放 A 写」→ 断言 B 未改、A 正确、B 的保存状态不被 A 的结果覆盖。

## X-06 旧结果覆盖新选择

**症状**：快速从 A 切到 B，A 的慢查询结果后到，把 B 的详情盖掉了。

**真因**：读路径没有 generation/queryId 校验，谁是最后一个返回谁就赢。

**现在由什么挡住**：契约 §10（数据读取）要求结果带 generation，UI 提交前核对"仍是当前 generation"；过期结果直接丢弃。对应测试 T-05。

## X-07 分析数据库把你的真实数据搞坏

**症状**：为了搞清表结构直接打开真实库，改了字段、跑了 `PRAGMA`、没 checkpoint，结果 App 数据错乱甚至被覆盖。

**真因**：没有"默认操作副本"的纪律。

**证据**：目标应用案例里 Core Data 库——App 启动时会重置 `ZACTIVE` 等字段（服务器同步语义），所以**在 App 未运行时改库，一启动就被覆盖**；另外 WAL 未 checkpoint 就改，写入进了 WAL 然后被 App 覆盖。

**现在由什么挡住**：A 档硬约束（`skills/replica-local-source`）：先 `cp` 到工作副本再动，路径约定与校验命令写在技能里；G7 之外的取证纪律。

**标准动作**：
```bash
cp "$APP_DB" /tmp/replica-work/$(basename "$APP_DB")
shasum -a 256 "$APP_DB" /tmp/replica-work/$(basename "$APP_DB")   # 两边一致才动手
sqlite3 /tmp/replica-work/xxx.db ".schema" > evidence/schema.sql  # 只读导出
# 绝不 sqlite3 "$APP_DB" "UPDATE ..."
```

## X-08 反编译代码能编译但行为静默错

**症状**：把还原出来的代码直接编进项目，能编译能跑，但某些字段永远是 `null`/`false`/`0`，某些功能"点了没反应"。

**真因**：反编译产物里有大量**空壳方法**——方法签名在、方法体被清零。本次案例实测 **1,163 个方法（1.9%）是空壳**，波及 621 个类型（Views 512 / ViewModels 110 / Util 85 / Dal 28）。比报错更危险，因为静默。

**现在由什么挡住**：R8（不许空壳实现）、R9（还原码只当规格书，不编入产品）。`00-体系总纲.md` §1.2 明确 A 档授权范围：**可以读，不可以编进去**。

**判定方法**：`grep` 方法体为 `{ }` / `{ return null; }` / `{ return default; }` 的数量；抽 20 个关键方法实际调用验证返回值。

## X-09 动了原程序之后 App 变空壳

**症状**：改动原应用的可执行文件之后，App 启动显示登录页、读不到自己的数据，或者干脆起不来。

**真因**：macOS 把应用组容器访问权和签名里的 Team ID 绑定。一旦签名链被破坏（TeamIdentifier 丢失、Hardened Runtime 掉位），系统就不再授权访问原来的容器——**改动带来的不是"多一点能力"，而是"整个账号态消失"**。

**本次结论**：这条路是死路。**红线的来源就是它**——R9 规定分析对象只读，不改二进制、不改签名、不改授权字段。

> 公开版说明：涉及修改原程序进程与签名的具体操作记录已从本文档移除，只保留结论与红线。取证方法本身（只读导出）见 `取证路径.md`。

## X-10 逆向读出乱码或半个选择器

**症状**：读 arm64 二进制里的指针，得到空串，或者选择器变成 `"For:"` `"nt:"` 这种半截。

**真因**：**arm64 chained fixup 指针掩码是 48 位**（`value & 0x0000FFFFFFFFFFFF`），不是常错的 51 位。取 51 位会多带 3 个头部位 → 地址偏移 6 字节。另外 Swift 类的 `class_ro_t` 布局不通用（`data` 指针低 3 位带 tag），按标准布局解会整体错位。

**正解**：权威布局用 `otool -oV`；指针一律 48 位掩码；Swift 类不复用 ObjC 的布局假设。

## X-11 静态找到方法，就断定「功能在这里」

**症状**：在还原代码或符号表里找到一个名字很像的方法，写进契约当结论；实现完发现原版行为完全不是那样。

**真因**：**方法存在 ≠ 有调用点**。目标应用实测某 50 方法的类，`__objc_selrefs` 调用点为 **0**，全二进制只有 2 个指针指向类名字符串——它是一个死代码类。另外 Swift 内部调用可能走静态派发、绕过 `objc_msgSend`，即使有替换点也拦不到。

**现在由什么挡住**：`skills/replica-local-source` 的第一条动作：**先证明有调用点，再谈结论**。查 `__objc_selrefs` 槽位是静态侧唯一可靠来源；证据等级只有到 A（实测）才允许进契约，C 级推断一律进 `unknowns.csv`。

> 这条教训与"怎么做"无关，与**证据等级**有关：静态可得的信息很多，能下结论的很少。

## X-12 在原应用的真实数据库上改动

**症状**：直接对原应用的库执行写操作，改动看起来生效了，重开 App 又变回去；严重时原应用数据损坏、需要重新登录同步。

**真因**：① 程序对库有自己的写入节奏与缓存，外部写入会被它下次落盘覆盖；② 部分字段由服务端同步语义决定，启动时按账号档位重置。

**正解**：**一律只读副本**。复制 → 校验哈希一致 → 在副本上 `.schema` 导出 → 原库操作前后哈希不变（证明没动过）。这一点由 R4 与 G1 强制。任何"要在真库上改一下"的念头，都说明取证方式选错了。

## X-13 上游英文技能与本地档位冲突

**症状**：`replica-skill` 的 recon 技能写着"绝不解包二进制、绝不读 JS bundle"，而你的实际需求就是要读源码拆数据库。执行时 AI 卡住或自我审查过度。

**真因**：上游是面向"商业克隆"的 clean-room 立场；A 档是本地自用、允许读源码。

**现在由什么挡住**：`skills/replica-local-source` 显式覆盖该条并在 `skills/replica-os/COMPAT.md` 里写明：**A 档覆盖"禁止看源码"；继续保留"不抄文案素材""测试自己的克隆而非原版服务器"**。冲突一律以本地档位为准，但每次覆盖都要写理由。

## X-14 三份模板三套编号，AI 各说各话

**症状**：同一个项目里，模板 A 说 R7 是"不许注释报错"，模板 B 说 R7 是"不编译反编译代码"，文档 C 用 C7 表示"catch 不全吞"。引用时全靠猜。

**真因**：没有单一事实来源；每次新增规则就另起一套编号。

**证据**：v1 实测——`templates/REDLINES.template.md` 是 R1–R17（权威）、`02` 是 R1–R14、`skill` 是 R1–R9+R13–R15+R17、`00` 是 C1–C12。**四套编号并存**，模板里专门加了一张对照表来解释，等于承认了问题。

**现在由什么挡住**：v2 只认 `00-体系总纲` §9 的 R1–R20，一张表；不再维护对照表；出现任何并行编号 = 违规。

## X-15 文档说"已修复"，代码里没修

**症状**：文档某处说"日期误触已修并复验"，另一处写"未修"；读者不知道该信哪个。

**真因**：正文里手写现状。文档随阶段写完就没人回头改，代码继续演进。

**证据**：v1 评估实测 `03` 里三对自相矛盾：第 57 行说日期 P0 已修并复验 / 第 364 行写未修；第 259 行说日期快捷入口已弱化 / 第 368 行写仍两套；第 366 行一边引用自适应备注框一边写仍固定高。

**现在由什么挡住**：**`STATE.md` 是唯一现状来源**（七态 + 证据路径 + 时间）。正文文档只写"设计意图与判据"，不写"现在做到哪"。

## X-16 门禁脚本写死某个项目的路径和数字

**症状**：门禁脚本换个项目就跑不了；或者在别的项目里"通过"了，因为它查的是 目标应用的 `evidence/schema/win-sqlite-schema.json`。

**真因**：门禁与项目耦合。

**证据**：v1 的 `rea-gate.sh` G3 里写死 `if (len(t) == 68)`、G1 只打印 SHA-256 不比对、G8 只要求"任意受控证据 > 0"、G9 只数引用处数。评估判定为 **AUD-06**：这类门禁不能作为自动放行依据。

**现在由什么挡住**：门禁全部 manifest 驱动（`.replica/gate.manifest.yml`），阈值、必需要件、N/A 都从配置读；新增项目只需写 manifest。

## X-19 界面像了但用户用起来别扭

**症状**：截图对比分数很高，但实际用起来：点「今天」要 0.3 秒、勾任务勾不上、按钮差 10px 导致误点、删了没提示。

**真因**：只对视觉，没对**操作行为**——点击数、热区、焦点、错误反馈、可撤销。

**证据**：本次实测——点日期框右侧微调箭头 1 秒内把日期改成 `2029/12/5` 且无撤销无提示；复选框热区仅 18px 导致"连点几次勾不上反而把整行选中"；切换「今天」293ms（后下推 SQL 才 3.8ms）；删除按钮与「已保存」同排极易误删；侧栏 912 vs 列表 500 自相矛盾。

**现在由什么挡住**：S9 的**行为 diff** 与视觉 diff 分开记分；UX 规格强制「热区最小尺寸」「点击数」「可撤销」「布局稳定」「焦点返回」；体验要求必须可判定（R11），"看着差不多"不算判据。

## X-20 采证采到一半范围失控

**症状**：本来只想复刻"任务管理"，结果一路挖到付费模型、同步协议、AI 功能、日历订阅，工期翻三倍。

**真因**：一开始没划"这一版做什么"。

**证据**：目标应用有 638 个界面、10 个模块、207 个 API 端点。全都做不现实。

**现在由什么挡住**：S0 的**不做清单 ≥5 条**（G0 机器判定）；S1 的 `features.csv` 用 `scope=out` + `original=no` + `progress=skip` + 理由明确写出排除项；S9 的 `skip` 行不计入分数（所以排除是合法的，但必须写明理由）。

## 附：翻车模式的元规律

把 20 条压缩成四句：

1. **凡是"等待"和"刷新"被简化成一句"应该没问题"，就会出事。**（X-01/03/04/06）
2. **凡是"条件"被合并成一句"看情况"，就会做错。**（X-02/05/19）
3. **凡是"证据"被简化成一句"我确认过"，就是假绿。**（X-08/11/15/17）
4. **凡是"范围"没有显式排除清单，就会失控。**（X-20/18/14）

这四句是 S2 蓝图与 G2/G3/G6 三道门的全部理由。
