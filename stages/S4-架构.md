# S4 · 架构

> 上游：冻结蓝图（`BLUEPRINT-LOCK` v1.0）· 下游：S5 设计系统 / S6 逐屏重建 · 门禁：G4

## 一句话

把冻结蓝图里的每个 `must` 功能，映射到**具体的表、具体的命令、具体的路由**，并先用一条最危险的竖切跑通「建→读→重启还在」；架构不是画图，是让「这个功能到底落在哪一行代码里」有唯一答案。

## 输入

| 从 S3 拿什么 | 文件 | 缺了就不许开工 |
|---|---|---|
| 冻结蓝图 | `BLUEPRINT-LOCK.md`（版本号 + 哈希一致） | 哈希与实算不一致 → 停。你可能在按幻觉版架构 |
| 数据字典 | `BLUEPRINT/data-dictionary.md`（`APPROVED`） | 缺 `E-` 字段定义 → `schema.sql` 只能靠猜 |
| 命令清单 | `BLUEPRINT/menus.csv` 的 `command` 列 | 有叶子无命令 → 该功能没有落点 |
| 联动矩阵 | `BLUEPRINT/linkage.csv`（`refresh_timing` 列） | 缺 → 事件/失效机制没法定 |
| 状态机 | `BLUEPRINT/state-machines.md` | 缺 → 生命周期实现会漏非法转换 |
| 技术约束 | `DECISIONS.md` 中的技术栈决策（若已定） | 未定 → S4 第一件事就是定它 |

## 动作序列

### 1 · 复算冻结哈希（5 分钟，必须先做）

```bash
python3 gates/run.py --stage G3 --project .      # 哈希对不上就停在这里
```

理由：S4 的一切推导都以 v1.0 为前提。哈希不符时继续做，等于把架构建在可能已被改过的契约上。

### 2 · 定技术栈（30 分钟，若 `DECISIONS.md` 未定）

按**硬约束优先**的顺序裁决，不许用加权总分掩盖硬约束失败：

| 顺序 | 硬约束 | 判据 | 不合格即淘汰 |
|---|---|---|---|
| 1 | 平台与体验 | 菜单/快捷键/焦点/输入法/拖拽能否原生做到 | 做不到即不合格，不许「后面再优化」 |
| 2 | 数据与离线 | 数据是否必须完全本地；是否要并发写 | 本地优先却选必须联网的方案 → 淘汰 |
| 3 | 分发形态 | A 档可 ad-hoc，B/C 档需签名与安装器 | 想不出怎么装到你机器上 → 淘汰 |
| 4 | 可维护性 | 单人能否维护、生态是否活跃 | 只有你能看懂 → 淘汰 |
| 5 | 成本 | 服务器/授权/构建时间 | 最后才比 |

落 `DECISIONS.md`：`D-0xx` 技术栈选择 + **落选方案的淘汰理由**（写理由，不写「综合考虑」）。

**竖切前置判断**（这一步决定 S4 成败）：先问「这个栈上最难的一件事是什么」，然后**只做那一件**：

| 产品类型 | 最难的那一件 | 竖切内容 |
|---|---|---|
| 任务管理（这一类） | 日期/重复规则的边界计算 + 关窗冲刷 | 建一条带重复规则的任务 → 改日期 → 关窗 → 重开验证 |
| 预约调度网站 | 时段冲突与并发预订 | 两个会话抢同一时段 → 一个成功一个被拒 → 刷新看到正确剩余 |
| 本地笔记 | 全文搜索 + 大文件导入 | 导入 10 万行文本 → 搜索 <200ms → 重启后索引还在 |
| 带提醒 | 定时器真的启动了 | 设 1 分钟后提醒 → 等它真的弹（不是调 `Tick()`） |

### 3 · 写 schema.sql（90 分钟）

从 `data-dictionary.md` 逐字段转，规则：

| 规则 | 说明 |
|---|---|
| 字段名照抄 | 字典写 `dueDate` 就写 `dueDate`，不改 `due_date`（全表统一改要记 `D-`） |
| `-` 不建 | 数据字典里 `-` 的列不建 |
| 枚举写 CHECK | 字典列出的实测枚举（如 `deleted ∈ {0,1,2}`）写成 `CHECK` 约束 |
| 软删除三态 | `0` 正常 / `1` 垃圾箱 / `2` 永久删除；`2` 不进任何查询 |
| 索引照原版 | 原版有索引的列组合照搬（S1 已取证）；自建的写理由 |
| 时间语义写注释 | `dueDate` 是本地日期还是 UTC 时刻必须写死（最高频跨时区 bug 源） |

```sql
CREATE TABLE TaskModel (
  id TEXT PRIMARY KEY, title TEXT NOT NULL,
  dueDate TEXT,        -- 本地日期 YYYY-MM-DD 无时区；NULL = 无到期日
  remindTime TEXT,     -- 本地时刻 ISO 8601；NULL = 无提醒
  repeat TEXT,         -- RRULE 子集；NULL = 不重复
  priority INTEGER DEFAULT 0 CHECK (priority IN (0,1,3,5)),
  projectId TEXT NOT NULL DEFAULT 'inbox',
  status INTEGER DEFAULT 0,                      -- 0 未完成 / 1 已完成
  deleted INTEGER DEFAULT 0 CHECK (deleted IN (0,1,2)),
  sortOrder INTEGER DEFAULT 0, modifiedTime TEXT NOT NULL
);
CREATE INDEX idx_task_due ON TaskModel(dueDate) WHERE deleted = 0;
```

判据：`schema.sql` 的每个字段名都能在 `data-dictionary.md` 找到同名条目；反向，数据字典里每个非 `-` 字段都在 `schema.sql` 出现。

### 4 · 建 TRACEABILITY.csv（60 分钟，本阶段核心产出）

9 列（SCHEMAS §12）：`feature_id` / `contract_ref` / `screen` / `menu_nodes` / `entities` / `commands` / `routes` / `tests` / `state`。

每个 `must & scope=in` 功能一行，且：

| 列 | 填法 | 不合格的样子 |
|---|---|---|
| `entities` | 具体表名或 `E` 编号，`;` 分隔 | 写「数据库」 |
| `commands` | 具体命令 ID，与 `menus.csv` 的 `command` 一致 | 写「保存」 |
| `routes` | 具体路由/方法名/窗口 ID | 写「界面」 |
| `tests` | `T-` 号，与契约 §16 一致 | 写「待补」 |
| `state` | 七态枚举值 | 写「进行中」 |

判据：`gates/run.py --stage G4` 能对这 9 列做机器判定——每行 `entities`、`commands` 非 `-`。

### 5 · 命令与路由清单（45 分钟）

从 `menus.csv` 的 `command` 列反推，去重后成清单。每条写清：

每条写清六项：**命令 ID**（如 `Cmd.SetTaskDueDate`）／**入参**（ID 在入队时捕获，不读「当前选中」，失效模式 05）／**事务边界**（单行 UPDATE 还是跨两表）／**完成信号**（可 await 的 `Task` 或事件名）／**失败返回**（结构化：成功/可重试/冲突/无权限/磁盘失败，不许只抛异常，R13）／**受影响联动**（`LK-xxx` 列表）。

路由清单同理（桌面端是窗口/视图 ID，Web 端是 URL path + method）。

### 6 · 竖切跑通（最关键的 2 小时）

**只做一条**，但必须端到端：

```
建表 → 建一条真实数据 → 读回来显示 → 关闭 → 重启 → 数据还在 → 关窗冲刷有结构化结果
```

证据落 `SPEC/vertical-slice.md`：

| 项 | 记录 |
|---|---|
| 命令 | 完整可复跑命令 |
| 建表耗时 | 毫秒数（带口径：冷/热启动） |
| 写入→读回 | 断言的具体值（不是「非空」） |
| 重启后 | 断言的具体值 + 日志/截图路径 |
| 冲刷结果 | 结构化输出原文 |
| 已知缺口 | 这条竖切没覆盖的东西（必须非空） |

判据：任何人照 `vertical-slice.md` 的命令重跑都能得到相同断言。

### 7 · 定构建优先级（30 分钟）

**竖切优先，不按「数据层→服务层→界面层」连续横切。** 四段顺序：① 最难的高风险竖切（步骤 2 判出的那件）→ ② 核心闭环（用户每天必做的那件事，端到端）→ ③ 高频辅助能力 → ④ 差异化模块。写进 `ARCHITECTURE.md` 的「构建顺序」段，每项标 `WP-` 编号（对应 S6 的 `BUILD/WORK-PACKAGES/`）。

### 8 · 写 ARCHITECTURE.md（60 分钟）

必含七段（对照 `templates/engineering/ARCHITECTURE.template.md`）：分层与职责边界、依赖方向、三条数据流（写/读/生命周期）、存储与索引、错误码、可观察性（日志位置与格式）、打包与更新。

**分层只写「不能做什么」也算合格**，这比「能做什么」更防越界：

```
Views      能：控件事件、弹窗、把事件转成命令   不能：写 SQL、业务规则、持有可变业务状态
ViewModels 能：串行写链、防抖、暴露完成信号    不能：直接 new 连接、处理窗口生命周期
Services   能：规则计算、解析、调度判定        不能：弹窗、依赖 UI 框架、依赖真实时间流逝
Data       能：SQL 下推、单列更新、索引        不能：UI 概念、业务默认值
```

### 9 · 跑 G4（10 分钟）

`python3 gates/run.py --stage G4 --project .`，退出码 0 才算结束。

## 细节级产出

| 文件 | 最小内容 | 判定它「够细」的标准 |
|---|---|---|
| `SPEC/ARCHITECTURE.md` | 七段齐；`must` 功能在「构建顺序」里有 `WP-` 编号 | 随便指一个 `must` 功能，能在 30 秒内找到它属于哪个 `WP-`、哪个层、哪条数据流 |
| `SPEC/schema.sql` | 全部实体与索引、CHECK 约束、时间语义注释 | 每个字段名都能在 `data-dictionary.md` 找到同名条目；反向也无遗漏；`sqlite3 /tmp/t.db < schema.sql` 能一次执行成功 |
| `SPEC/TRACEABILITY.csv` | 9 列，每个 `must & in` 功能一行 | `entities`、`commands` 非 `-`；`commands` 与 `menus.csv` 的 `command` 能对上；行数 = `must & in` 功能数（脚本可核） |
| 命令/路由清单 | 每命令：ID/入参/事务边界/完成信号/失败返回/受影响 `LK-` | 每条命令的入参里有「不可变 ID」而不是「当前选中」；失败返回是结构化枚举 |
| `SPEC/vertical-slice.md` | 命令 + 耗时 + 断言值 + 重启验证 + 冲刷结果 + 已知缺口 | 照命令重跑能得到相同断言值；「已知缺口」非空（诚实项） |
| `DECISIONS.md` 追加 | 技术栈 `D-` + 落选方案淘汰理由 | 落选理由是具体的硬约束失败，不是「综合考虑」 |

## 门禁 G4

### 机器判定（`gates/rules/g4.py`）

| # | 检查项 | 期望 | 不通过怎么修 |
|---|---|---|---|
| 1 | `schema.sql` 可执行 | `sqlite3 <tmp> < schema.sql` 退出码 0 | 修语法；约束冲突逐条处理 |
| 2 | schema 与数据字典字段一致 | `data-dictionary.md` 每个非 `-` 字段在 `schema.sql` 出现，且反向无多余字段（多余必须有 `D-` 说明） | 补齐或删掉多余字段 |
| 3 | 每个 must 功能有映射 | `features.csv` 中 `must & scope=in` 的功能，在 `TRACEABILITY.csv` 均有行且 `entities`、`commands` 非 `-` | 补映射；补不了 → 该功能其实不可实现，走变更单 |
| 4 | `TRACEABILITY.csv` 行数与 must 功能数一致 | 数量相等 | 缺行补齐，多行删除或标 `deprecated` |
| 5 | 命令与菜单对齐 | `menus.csv` 非 separator/label 节点的 `command`，在命令清单里都能找到 | 补命令定义或修正 ID |
| 6 | 竖切证据存在 | `SPEC/vertical-slice.md` 存在且含「重启后断言」「冲刷结果」两段 | 补做竖切，不许跳过 |
| 7 | 无未决技术选型 | `DECISIONS.md` 有技术栈 `D-`；`ARCHITECTURE.md` 无 `待定`/`TBD`/`选型中` | 定下来并写落选理由 |

### 人工判定（Lead，Agent 不得自批）

| # | 判什么 | 判定问句 |
|---|---|---|
| 1 | 竖切是否真的跑通了「重启还在」 | 「把命令给我，我当场跑一遍。」 |
| 2 | 分层是否真的防住了越界 | 「这条 SQL 写在哪一层？如果写在 View 里，会有什么机制拦住？」 |
| 3 | 命令是否携带不可变 ID | 「用户改了 A 立刻切到 B，这个命令会改谁？」 |
| 4 | 构建顺序是否竖切优先 | 「前三个 WP 是不是都能单独运行起来给用户看？」 |
| 5 | 「最难的那一件事」是否真找对了 | 「如果你判断错了最难的点，两周后会卡在哪？」 |

## 常见翻车点

| # | 症状 | 真因 | 对策 |
|---|---|---|---|
| 1 | 跳过竖切直接写业务代码，技术栈坑集中爆发 | Phase 0 没做 | 步骤 6 强制跑一条端到端；G4 机器判定 6 要求证据文件存在 |
| 2 | `schema.sql` 与数据字典字段名不一致，S7 才发现 | 手写 schema 没对照 | G4 双向字段比对；先脚本生成再手改 |
| 3 | 每个功能都能映射，但没一个能跑 | 映射表是「填出来的」，不是「实现出来的」 | 竖切证据 + `state` 列必须按七态推进，不许批量 `APPROVED` |
| 4 | 改了 A 结果 B 被改（失效模式 05） | 命令入参是「当前选中」而非入队时捕获的 ID | 命令清单强制写「不可变 ID」；人工判定 3 专查这条 |
| 5 | 关窗丢数据（失效模式 03） | 架构期没设计冲刷点 | 竖切必须含「关窗冲刷有结构化结果」（R3）；分层的 VМ 层「能」列必须写暴露完成信号 |
| 6 | 构建警告滚雪球（R6） | 没把警告计数纳入竖切 | `vertical-slice.md` 记录构建输出；0 错误 0 警告写进完成定义 |
| 7 | 性能数字不可比（R12） | 竖切里的耗时没写口径 | 每个耗时都写「冷/热启动 + 库规模 + 机器」 |
| 8 | 架构写得像论文，实现时没人看 | 七段写成了原则不是判据 | 每段必须有「不能做什么」清单与具体文件路径 |

## 示例

### 示例 1 · TRACEABILITY.csv 片段（目标应用场景）

```csv
feature_id,contract_ref,screen,menu_nodes,entities,commands,routes,tests,state
F-DATE-EDIT,contracts/C-F-DATE-EDIT.md,S-02,M-DATE;M-DATE-SUB-03;M-DATE-CLEAR,TaskModel,Cmd.SetTaskDueDate;Cmd.ClearDueDate,DetailViewModel.SetDueDateAsync,T-101;T-102;T-103,APPROVED
F-TASK-COMPLETE,contracts/C-F-TASK-COMPLETE.md,S-01,M-TASK-CHECK,TaskModel;DailyStat,Cmd.CompleteTask,MainViewModel.ToggleCompleteAsync,T-201;T-202,APPROVED
F-REPEAT-SET,contracts/C-F-REPEAT.md,S-02,M-DATE-SUB;M-DATE-SUB-03,TaskModel;RepeatRule,Cmd.SetRepeatWeeklyWorkdays,DetailViewModel.SetRepeatAsync,T-301;T-302,APPROVED
```

注意 `F-DATE-EDIT` 的 `menu_nodes` 有三个：改日期不是一个菜单节点，是一组。**漏掉 `M-DATE-CLEAR` 就意味着「清除日期」这条路径在架构里没有落点**——这是最常见的映射缺失。

### 示例 2 · 竖切证据（`SPEC/vertical-slice.md` 的实样）

| 项 | 记录 |
|---|---|
| 命令 | `rm -f /tmp/vs.db && sqlite3 /tmp/vs.db < SPEC/schema.sql && python3 e2e/vs_probe.py --db /tmp/vs.db` |
| 建表耗时 | 冷启动 234ms / 热 41ms（20 张表，macOS arm64，SSD） |
| 写入→读回 | 写入 `{title:"竖切任务", dueDate:"2026-10-23"}`，读回 `title=="竖切任务" && dueDate=="2026-10-23"` |
| 重启后 | 关闭连接、重开新连接，`SELECT dueDate FROM TaskModel WHERE id=?` → `2026-10-23` |
| 冲刷结果 | `{"status":"flushed","pending":0,"failed":0}`（结构化，非布尔） |
| 已知缺口 | 未覆盖多窗口并发写；未覆盖磁盘满 |

`已知缺口` 这一行必须非空。竖切全绿但「缺口：无」通常意味着竖切做得太浅。

### 示例 3 · 命令定义（含不可变 ID）

```yaml
Cmd.SetTaskDueDate:
  params: { taskId: "入队时捕获，不可变", date: "本地日期 YYYY-MM-DD", keepTime: "bool" }
  transaction: 单行 UPDATE TaskModel
  completion: Task PendingSave（可 await）
  failure: { retryable: [...], conflict: [...], permission: [...], disk: [...] }
  affects: [LK-001, LK-002, LK-003, LK-004, LK-005, LK-006]
```

「入队时捕获，不可变」就是失效模式 05 的解药。

## 退出与交接

| 交接物 | 门槛 | S5 / S6 怎么用 |
|---|---|---|
| `SPEC/ARCHITECTURE.md` | 七段齐、构建顺序有 `WP-` | S6 按 `WP-` 顺序建；S5 按分层定组件边界 |
| `SPEC/schema.sql` | 可执行、与数据字典一致 | S7 直接用它初始化数据库；S6 的假实现按它写签名 |
| `SPEC/TRACEABILITY.csv` | 行数 = must 功能数、`entities`/`commands` 非 `-` | S6 每建一个功能就更新 `state` 列 |
| 命令/路由清单 | 每命令有完成信号与失败枚举 | S6 的「数据接口假实现」照此写稳定签名（00 §2.1） |
| `SPEC/vertical-slice.md` | 有重启断言与冲刷结果 | S7 以此为模板扩展 |

**交接状态要求**：G4 退出码 `0`；竖切证据文件存在；无未决技术选型。

**S6 与 S7 可交错**（00 §2.1），但 S6 的「数据接口」必须先是**以假实现落地的稳定签名**——换真实现时不许改界面代码。

**下一个接手的人需要知道的唯一一句话**：每个 must 功能都已经指定了落在哪个表、哪个命令、哪个路由；找不到落点的功能说明它其实做不了，去走变更单。
