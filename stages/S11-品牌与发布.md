# S11 · 品牌与发布

> 上游：通过 G8/G9 的构建 · 门禁：G11 · **本阶段按档位严重分叉：A 档只做本地 runbook，B 档加安装升级，C 档才做品牌与商店**

## 一句话

按你的档位交付：A 档（本地自用）只把「怎么启动、怎么备份、怎么恢复、怎么迁移、怎么卸载干净」写成一份能照着做的 runbook；B 档加安装包与升级路径；C 档才做品牌清扫、落地页、商店合规与支付对账。

## 输入

| 从哪来 | 文件 | 缺了就不许开工 |
|---|---|---|
| 通过的门 | G8 + G9 记录 | 任一未过 → 停，没通过门的构建不许进发布 |
| 档位 | `.replica/gate.manifest.yml` 的 `tier` | 缺 → 不知道走哪个分支 |
| 构建产物 | 可执行文件/安装包 + 版本号 + 构建时间 | 缺版本号 → 出问题无法定位 |
| 数据路径 | 实际数据目录（含 WAL 三件） | 缺 → 备份/恢复写不出来 |
| 已知差异 | `DECISIONS.md` 的「刻意不同」条目 | 缺 → 发布说明无法解释差异 |
| 备份恢复实测 | S7 的记录 | 缺 → runbook 只能是猜测 |

## 动作序列

### A 档：本地自用（默认路径，只做这一节就够）

A 档**不做**品牌命名、商标查询、商店文案、落地页、支付集成、域名部署——这不是「以后再说」，是明确的范围外，要写进 `PROJECT.md` 不做清单（四段式）。

#### A1 · 启动脚本（30 分钟）

```bash
#!/usr/bin/env bash
set -euo pipefail                      # run.sh：固定数据目录，避免路径漂移
APP_DIR="$(cd "$(dirname "$0")" && pwd)"
export DATA_DIR="${DATA_DIR:-$HOME/Library/Application Support/<产品名>}"
mkdir -p "$DATA_DIR"
exec "$APP_DIR/bin/<可执行文件>" --data-dir "$DATA_DIR" "$@"
```

四条要求：`DATA_DIR` 有默认值且可用环境变量覆盖／目录不存在时自动建／参数透传 `"$@"`／`chmod +x` 后 `./run.sh --help` 有输出。

#### A2 · 备份（30 分钟，必须三件一起拷）

```bash
#!/usr/bin/env bash
set -euo pipefail                      # backup.sh：db + wal + shm 三件一起拷
DATA_DIR="${DATA_DIR:-$HOME/Library/Application Support/<产品名>}"
DEST="${1:-$HOME/Backups/<产品名>/$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$DEST"
sqlite3 "$DATA_DIR/app.db" "PRAGMA wal_checkpoint(TRUNCATE);"   # 先合并 WAL 再拷
cp "$DATA_DIR"/* "$DEST/"; echo "备份完成：$DEST"; ls -la "$DEST"
```

判据：备份后 `DEST` 里至少有三个文件（`app.db`、`app.db-wal`、`app.db-shm`，或 checkpoint 后仅 `app.db`）。

#### A3 · 恢复（20 分钟）

```bash
#!/usr/bin/env bash
set -euo pipefail
DATA_DIR="${DATA_DIR:-$HOME/Library/Application Support/<产品名>}"
SRC="${1:?用法: restore.sh <备份目录>}"
[ -f "$SRC/app.db" ] || { echo "备份目录里没有 app.db：$SRC" >&2; exit 1; }
./backup.sh "$HOME/Backups/<产品名>/pre-restore-$(date +%Y%m%d-%H%M%S)"   # 先备份当前数据
cp "$SRC"/* "$DATA_DIR"/
echo "恢复完成，请启动应用验证：$DATA_DIR"
```

**恢复必须做实测**，不是写完就算：

实测四步：① 记下一条任务的确切字段值（如 `dueDate=2026-10-24`）→ ② 改掉它、备份、再改一次（现在值 ≠ 备份时的值）→ ③ 从备份恢复并启动（读回值 == 备份时的值）→ ④ **再启动一次**（值仍是备份时的值，排除内存缓存）。

#### A4 · 迁移演练（30 分钟，换机器/换目录）

五步：旧机器备份 → 拷备份目录到新机器 → 新机器装应用 → 恢复 → 启动 → 断言 3 条抽样数据。判据：3 条抽样字段值逐一相同、条数相同、附件/导出文件也能打开。

#### A5 · 卸载检查（20 分钟）

```bash
ls -la "$HOME/Library/Application Support/<产品名>"      # 主数据
ls -la "$HOME/Library/Caches/<产品名>" 2>/dev/null        # 缓存
ls -la "$HOME/Library/Logs/<产品名>" 2>/dev/null          # 日志
ls -la "$HOME/Library/Preferences/<产品名>"* 2>/dev/null  # 配置
```

处置规则：**主数据目录保留**（先提示已备份，本地自用最怕误删数据）／缓存删除（可再生）／日志删除或保留最近 7 天／配置删除（重装要干净）／**单实例锁文件删除**（否则重启后可能拿不到锁）。

判据：写下「卸载后哪些目录还在」的清单，并实际验证一次。

#### A6 · 日志位置（15 分钟）

五项：**位置**固定（如 `~/Library/Logs/<产品名>/app.log`）并写进 runbook／**轮转** 10MB × 3 起步（否则跑三个月占满盘）／**脱敏**（不出现密钥、token、完整用户数据，R13 配套）／**级别**可运行时调整，默认 `info`／**崩溃可查**（留最后 N 行缓冲，否则只剩「它崩了」）。

#### A7 · 写 local-runbook.md（40 分钟）

`REPORT/release/local-runbook.md` 必含八节，每节都要能照抄执行：**1 这是什么**（一句话 + 版本号 + 构建时间，版本号与可执行文件一致）／**2 怎么启动**（`run.sh` 用法 + 数据目录默认路径）／**3 怎么备份**（`backup.sh` 用法 + 备份到哪 + 多久备一次）／**4 怎么恢复**（`restore.sh` 用法 + 恢复前自动备份）／**5 怎么迁移**（换机器五步）／**6 怎么卸载**（删什么、**留什么**、验证命令）／**7 出问题怎么办**（日志在哪 + 常见故障三条，每条有具体命令）／**8 已知限制**（与原版的差异 + 不支持的场景，每条有 `D-` 编号）。

#### A8 · 干净机器验证（40 分钟，A 档的「发布门」）

G11 对 A 档的要求是「干净机器装得上、开得了、数据不丢、卸得干净」。A 档没有安装器，等价验证是：

四项：**装得上**（另一用户账号或另一台机器，只拷 `run.sh` + 二进制能启动）／**开得了**（首次启动无报错，能建第一条数据）／**数据不丢**（备份→删数据→恢复→三条抽样值一致）／**卸得干净**（按 runbook 卸载后残留清单与记录一致）。

### B 档：半自用（A 档 + 安装/升级/卸载门 + 数据迁移演练）

在 A 档全部做完的基础上追加：

六项：**安装器**（`.dmg`/`.pkg`/`.exe`/`.AppImage`，干净机器双击能装）／**签名**（`codesign -v` 通过）／**升级路径**（旧→新，真实数据不丢，用旧版造数据后升再断言值）／**schema 迁移**（版本号 + 迁移脚本 + 回滚命令）／**卸载器**（残留检查输出为空）／**崩溃上报**（至少本地崩溃日志，位置进 runbook）。

**升级门是最容易漏的一条**：绝大多数事故不是「装不上」，是「升级后数据打不开」。必须用**真实旧版数据**做升级演练，不能用自己造的干净数据。

### C 档：商业（全部 + 品牌清扫 + 上架合规 + 支付对账）

在 B 档基础上追加，**不做完不许对外**：

九项：**品牌切割**（新名字/配色/图标/文案，`sweep.py` 0 命中）／**商标与域名**（可用性查询，有结论与风险告知）／**素材来源台账**（每个图标/字体/图片的许可证与来源，无「来源不明」）／**落地页**（围绕 S10 的定位角度，无原版名、无未验证宣称）／**商店文案**（`listing.py` 通过）／**支付对账**（成功/失败/重复通知/退款/恢复购买/对账，六条各一实测记录）／**隐私与数据**（数据在哪、怎么删、怎么导出，声明与实现一致）／**支持入口**（渠道 + 承诺时限）／**部署预检**（`preflight.md` 四项全绿）。

```bash
python3 replica-skill/replica-brand/sweep.py . --avoid "<原版应用名>"   # 必须 0 命中
python3 replica-skill/replica-launch/listing.py launch/listing.json     # 长度与仿冒检查
```

## 门禁 G11

### 机器判定（`gates/rules/g11.py`，按 `tier` 分流）

**A 档（四判）**

| # | 检查项 | 期望 | 不通过怎么修 |
|---|---|---|---|
| 1 | 启动脚本可执行 | `run.sh` 有执行位且 `--help` 有输出 | 补脚本 + `chmod +x` |
| 2 | 备份/恢复实测记录 | runbook 有命令与结果，含「再启动一次」 | 真做一次并贴输出 |
| 3 | 卸载无残留验证 | runbook 有「删什么/留什么」+ 实测 `ls` 输出 | 真卸载一次并贴输出 |

**B 档追加**：安装包存在且干净机器能装／升级用**真实旧数据**（记录里有旧版本号 + 断言值）／schema 迁移有回滚命令且实测。

**C 档追加**：`sweep.py` 0 命中／`listing.py` 通过／支付六路径（成功/失败/重复通知/退款/恢复购买/对账）各一条实测记录／素材台账每行有许可证与来源。

## 常见翻车点

| # | 症状 | 真因 | 对策 |
|---|---|---|---|
| 1 | A 档做了 C 档的事，工期翻三倍 | 档位没落到门禁 | `.replica/gate.manifest.yml` 的 `tier` 驱动 G11 分流；A 档的 `na_approved` 写明「商业项 N/A」 |
| 2 | 备份只拷了 `.db`，恢复后少数据 | WAL 未 checkpoint，数据在 `-wal` 里 | 三件一起拷，或先 `wal_checkpoint(TRUNCATE)` |
| 3 | 恢复完没验证，真出事了发现备份是坏的 | 只做了备份没做恢复演练 | 恢复必须实测：改值→备份→再改→恢复→断言具体值 |
| 4 | runbook 写得像说明书，用时找不到命令 | 只有描述没有可复制的命令块 | 每节必须能照抄执行；命令用代码块 |
| 5 | 升级后打不开数据（B/C 档） | 用干净数据测升级，没用真实旧数据 | 用真实旧版数据演练；schema 迁移带回滚 |
| 6 | 卸载后还有残留进程/锁 | 单实例锁文件没清 | 卸载清单里列锁文件；实测检查 |
| 7 | 日志不轮转，跑三个月把盘占满 | 没设轮转 | 10MB × 3 起步 |
| 8 | 对外文案里留着原版名字 | 没跑 sweep | C 档 `sweep.py` 0 命中才许发布 |
| 9 | 已知限制不写，用户（或你三个月后）踩坑 | 觉得「这不重要」 | runbook 第 8 节强制每条带 `D-` |

## 示例

### 示例 1 · A 档 runbook 第 3 节（备份）的实样

```markdown
（local-runbook.md 的「## 3 怎么备份」小节正文）

```bash
# 一键备份（三件一起拷）
./backup.sh
# → 备份到 ~/Backups/我的任务/20261023-181500/
```

**多久备一次**：每周日 + 每次大改数据前。**验证备份可用**（每月一次）：
```bash
ls -la ~/Backups/我的任务/20261023-181500/      # checkpoint 后仅 app.db 也算完整
sqlite3 ~/Backups/我的任务/20261023-181500/app.db "SELECT COUNT(*) FROM TaskModel;"
```
**最坏会丢多少**：距上次备份之间的所有改动。
```

这一段的价值在最后一行——它直接回答了「备份能救你多少」，而不是「建议定期备份」。

### 示例 2 · 备份恢复的实测记录

```text
1) 记下抽取值：title="给客户回电" dueDate=2026-10-24 priority=5
2) 改掉它 → ./backup.sh → ~/Backups/我的任务/20261023-181500/
3) 再改一次（现在值 ≠ 备份值）
4) ./restore.sh ~/Backups/我的任务/20261023-181500/ → 启动 → 查库：
   sqlite3 "$DATA_DIR/app.db" "SELECT title,dueDate,priority FROM TaskModel WHERE id='t-001';"
   → 给客户回电|2026-10-24|5        —— 与第 1 步一致
5) 再启动一次（排除缓存）→ 同上 —— 通过
```

第 7 步是关键：只启动一次可能是内存缓存，重启后才证明数据真的落盘了。

### 示例 3 · 卸载残留清单（A 档）

| 路径 | 处置 | 实测结果 |
|---|---|---|
| `~/Library/Application Support/我的任务/` | **保留**（含全部数据） | 存在，含 `app.db` |
| `~/Library/Caches/我的任务/` | 删除 | 已删，无残留 |
| `~/Library/Logs/我的任务/` | 保留最近 7 天 | 存在，3 个文件 |
| `~/Library/Preferences/com.example.mytask.plist` | 删除 | 已删 |
| `/tmp/mytask.lock`（单实例锁） | 删除 | 已删 |

「保留」的两项是刻意的：本地自用最怕误删数据，所以卸载默认不动数据目录，并在 runbook 里明说。
