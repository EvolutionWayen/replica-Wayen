# S8 · 测试

> 上游：蓝图流程 + 已实现功能 · 下游：S9 一致性评分 · 门禁：G8

## 一句话

用例从 S2 的契约 §16 就已经开始写了，S8 只做三件事：补齐缺口、真跑、把「连跑三次都不抖」变成可核对的记录——**测试的唯一目的是让「用户一用就崩」这类事在交付前暴露**。

## 输入

| 从哪来 | 文件 | 缺了就不许开工 |
|---|---|---|
| 契约用例 | `contracts/*.md` §16（正常/负向/边缘/跨页面/退出重启） | 某契约 §16 少于 5 条 → 先补契约（走变更单），不许在测试里补 |
| 流程 | `BLUEPRINT/flows.md`（每流程有失败与取消表、边界表） | 缺边界表 → 边缘用例写不出来 |

| 红线 | `REDLINES.md`（R1–R5、R13） | 缺 → 会写出假绿测试 |

## 动作序列

### 1 · 建 test-plan.md（每流程 30 分钟）

每用例固定一行（SCHEMAS §14）：

```
| T-xxx | FL-xx | 类型(正常/负向/边缘/跨页面/生命周期) | 步骤 | 期望（具体值） | 自动化(是/否) |
```

**「期望」列是全表的灵魂**。判定标准：这一列必须写能被机器比较的值。

| 不合格的期望 | 合格的期望 |
|---|---|
| 保存成功 | `dueDate == "2026-10-24"` 且 `list[0].dateText == "明天"` |
| 提醒触发 | 1 分钟后弹窗出现，`window.title == "提醒"`，`window.taskId == "t-001"` |
| 角标更新 | `sidebar.today == 916` 且 `916 + 43 == 959`（与视图切换后总数一致） |
| 界面刷新 | 主列表第 3 行文本从 `10/23` 变为 `10/24`，第 1、2 行文本未变 |
| 错误提示正常 | 状态文案含「保存失败」且**不含**「已保存」 |

每流程至少覆盖：

| 类型 | 条数 | 内容 |
|---|---|---|
| 正常 | ≥1 | happy path，断言最终状态的具体值 |
| 负向 | ≥1 | 非法输入/无权限/失败，断言不崩溃且有可读提示 |
| 边缘 | ≥1 | 跨月/闰日/时区变更/空值/极长文本/0 条与 1 万条 |
| 跨页面 | ≥1 | 六面联动（来自 `linkage.csv` 的 `test_ref`） |
| 生命周期 | ≥1 | 写 → 立即退出 → 重启 → 断言值还在 |

### 2 · 三类必测的「硬用例」（20 分钟，先写这三类）

这三类能挡住 80% 的真实事故，**优先写**：

#### 2.1 无等待即时关闭（R1/R3）

```text
改一个字段 → 不 sleep、不等 → 立即关闭/强杀 → 重开 → 断言具体值
```

**反例**（就是 目标应用项目踩过的）：测试里写 `await sleep(200)` 等写入完成——它恰好等到写入成功，把竞态伪装成绿灯。

#### 2.2 改 A 不动 B（失效模式 05 / 单列更新）

```text
给任务设 title/notes/priority/dueDate → 只改 title → 断言 notes/priority/dueDate 全未变
```

这条用例能挡住「整对象回写把未读列清空」这类静默数据损坏。

#### 2.3 零调用点（失效模式 08 变体）

```text
设 1 分钟后提醒 → 等待真实时间 → 断言弹窗真的出现（不许直接调内部 tick）
```

「引擎逻辑全对但定时器没启动」是 本项目的真实事故：54 个测试全绿，提醒永不触发。

### 3 · 写 e2e 用例（每流程 1 小时）

`e2e/` 下每个流程一个文件，命名 `FL-xx-<短名>`。要求：

| 要求 | 判定 |
|---|---|
| 驱动真实 UI 路径 | 不许直接调 ViewModel 抄近路（否则「界面没接线」测不出来） |
| 断言具体值 | 见步骤 1 的期望列 |
| 每用例独立数据目录 | 用例之间不串库（静态单例会串，是假绿温床） |
| 无固定延时 | `grep -c "sleep"` 在 e2e 目录为 0 |

### 4 · 故障注入补齐（1 小时）

S7 已做了四类（磁盘只读/磁盘满/数据库损坏/强杀）。S8 补齐组合与回归：

| 组合 | 期望 |
|---|---|
| 磁盘只读 + 连改 3 次 | 3 次都保留草稿，不崩溃 |
| 磁盘满 + 关窗 | 冲刷返回 `failed=N`，提示明确，不静默退出 |
| 损坏 + 恢复备份 | 恢复后能启动且数据在 |
| 强杀 + 立即重开（100 轮） | 0 次丢失（这条最能暴露 fire-and-forget） |

### 5 · 连跑三次（30 分钟，R5）

```bash
for i in 1 2 3; do
  python3 -m pytest e2e tests -q --json-report --json-report-file=TEST/results/$(date +%Y%m%d)-run$i.json
done
# 或任意测试框架；关键是落三个结果文件，且用例数一致
```

判据三条：① 三次全 pass；② 三次的 `total` 数完全相同（用例数漂移说明有测试被跳过）；③ `failed=0`。

**单次绿不可信**。静态单例跨测试串库会让单文件跑绿、全量跑红。

### 6 · 记 bug（持续）

`TEST/bugs.md` 固定表格：`| BUG-xxx | 严重度 S1/S2/S3 | 状态 | 现象 | 复现步骤 | 证据 | 修复提交 |`。

| 严重度 | 定义 | 处置 |
|---|---|---|
| S1 | 数据丢失/损坏、崩溃、无法启动 | **阻断交付**，=0 才能过 G8 |
| S2 | 核心功能不可用或结果错误 | **阻断交付**，=0 才能过 G8 |
| S3 | 体验问题、文案、布局 | 记入清单，可带病交付（需产品官接受） |

规则：只追加不删行；改状态要写修复提交号；**修复后必须重放原失败步骤**（R7 的变体：不许改断言让它过）。

### 7 · 覆盖率检查（20 分钟，不是为了数字好看）

```bash
# 关键不是百分比，是「每个 must 功能是否至少一条 e2e」
python3 - <<'PY'
import csv
must={r['feature_id'] for r in csv.DictReader(open('BLUEPRINT/features.csv',encoding='utf-8'))
      if r['priority']=='must' and r['scope']=='in'}
covered=set()
for r in csv.DictReader(open('SPEC/TRACEABILITY.csv',encoding='utf-8')):
    if r['tests'] not in ('-',''): covered.add(r['feature_id'])
print('must:',len(must),'有测试:',len(must&covered),'缺:',sorted(must-covered))
PY
```

## 门禁 G8

### 机器判定（`gates/rules/g8.py`）

| # | 检查项 | 期望 | 不通过怎么修 |
|---|---|---|---|
| 1 | 无 S1/S2 打开的缺陷 | `bugs.md` 中 `severity ∈ {S1,S2}` 且 `status != closed` 的条数 = 0 | 修完并重放原失败步骤 |
| 2 | 每 must 功能 ≥1 e2e | `TRACEABILITY.csv` 中每个 must 功能 `tests` 非 `-`，且对应用例存在 | 补用例 |
| 3 | 连跑 ≥3 次稳定 | 最新 3 个 `results/*.json` 全部 `failed=0` 且 `total` 相同 | 定位 flaky 根因（多为等待式同步/静态单例） |
| 4 | 无等待式同步 | `e2e/`、持久化测试目录 `sleep\|Thread.Sleep` 命中数 = 0（R1） | 改 await 完成信号 |
| 5 | 期望值不含模糊词 | `test-plan.md` 的「期望」列不含单独的「成功/正常/刷新/正确」 | 改成具体值 |
| 6 | 生命周期用例存在 | 每流程 ≥1 条「写→退出→重启→断言」 | 补用例 |
| 7 | 结果文件可追溯 | 每个 `results/*.json` 含 `commit` 与 `run` 时间 | 补字段 |
| 8 | 失败用例不静默跳过 | 三次的 `total` 一致 | 查 `skip` 与条件跳过 |

### 人工判定（验证官 + 产品官）

| # | 判什么 | 判定问句 | 判定人 |
|---|---|---|---|
| 1 | 测试严格度 | 「这个持久化测试用的是真文件还是内存库？断言查的是具体值吗？」 | 验证官 |
| 2 | 是否走了捷径 | 「e2e 是驱动真实控件，还是直接调 ViewModel？」 | 验证官 |
| 3 | 修复是否重放了原失败 | 「原来那条用例现在过了吗？给我看它跑的过程。」 | 验证官 |
| 4 | 真机手感 | 「用真鼠标点一遍核心流程，你觉得哪个地方别扭？」 | 产品官 |

## 常见翻车点

| # | 症状 | 真因 | 对策 |
|---|---|---|---|
| 1 | 测试全绿但用户一用就崩（失效模式 04） | 用 `sleep` 猜完成；内存库测持久化 | R1/R4/R5 + 三类硬用例（步骤 2） |
| 2 | 单文件绿、全量红 | 静态单例跨测试串库 | 每用例独立数据目录 + 夹具显式重置；全量连跑 ≥3 次 |
| 3 | 测试改了断言让它通过 | 把门禁当障碍 | R7 变体：只许加不许弱化；修复后重放原失败步骤 |
| 4 | 引擎逻辑对但功能没接线 | 测试直接调内部方法，绕过真实接线 | 零调用点护栏：断言定时器启用 / 事件真实触发 |
| 5 | 覆盖率很高但核心路径没测 | 覆盖率按行数算，不看关键路径 | 按 must 功能 × e2e 数量算，不看行覆盖率 |
| 6 | 三次跑用例数不一致 | 有条件跳过 / 依赖外部状态 | G8 判定 8：三次 `total` 必须相同 |
| 7 | 只有 happy path，负向与边界全空 | 正向最容易写 | 每流程五类类型各有 ≥1 条，G8 抽查 |
| 8 | S3 缺陷堆积，交付时说不清 | 没有分级与关闭标准 | S1/S2 阻断、S3 需产品官书面接受；只追加不删行 |

### 示例 2 · 三类硬用例的反例与正例

| 用例 | 反例（假绿） | 正例 |
|---|---|---|
| 即时关闭 | `save(); await sleep(200); assert(saved)` | `save(); close(); assertEqual(reopen().dueDate, "2026-10-24")` |
| 改 A 不动 B | `update_title(); assert(task.title == "新")` | `update_title(); assert(t.notes=="原备注" && t.priority==3 && t.dueDate=="2026-10-23")` |
| 提醒触发 | `engine.tick(now); assert(due)` | `set_reminder(+1min); wait_real(70s); assert(window.id=="t-001")` |

### 示例 3 · bugs.md 的一行

```
| BUG-012 | S2 | closed | 改日期后提醒仍在旧时间弹 | 1)设15:00提醒 2)改日期到明天 3)等到15:00 | TEST/results/20261023-run2.json | a3f9c21 |
```

「现象」写成了一句话讲清的错误行为，「复现步骤」三步可重放，「证据」指向结果文件而不是「已修」。
