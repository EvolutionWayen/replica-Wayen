# S7 · 后端与本地能力

> 上游：S4 架构 + S6 界面（假实现）· 下游：S8 测试 · 门禁：G7

## 一句话

把 S6 的假数据接口换成**真文件持久化**：写进串行链、关窗能冲刷、失败不丢草稿、重启数据还在；本地自用档不需要服务器，但「数据不丢」这条比任何功能都硬。

## 输入

| 从哪来 | 文件 | 缺了就不许开工 |
|---|---|---|
| schema | `SPEC/schema.sql`（可执行） | 执行报错 → 先修 schema，G4 应已保证 |
| 命令清单 | S4 命令签名 + 失败枚举 | 缺失败枚举 → 写不出结构化冲刷结果（R3） |
| 界面层 | `src/` 已接线（假实现） | 界面还在直接连库 → 先改回签名调用，否则换真实现要改界面 |
| 联动清单 | `linkage.csv`（提醒面尤其关键） | 缺 → 不知道哪些写操作要触发调度重算 |
| 红线 | `REDLINES.md`（R1–R5、R13、R14） | 缺 → 会写出「测试绿但用户丢数据」的代码 |

## 动作序列

### 1 · 落真持久化（2 小时）

```bash
# A 档：数据库默认操作副本；真实库只读（失效模式 07）
cp "<真实库>" /tmp/work.db
sqlite3 /tmp/work.db "PRAGMA journal_mode=WAL;"    # 期望返回 wal
sqlite3 /tmp/work.db "PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON;"
sqlite3 /tmp/work.db ".schema" > evidence/db/schema-actual.txt
```

要点：

| 项 | 要求 | 判定 |
|---|---|---|
| 真文件 | 数据库必须是磁盘文件，**禁止 `:memory:`**（R4） | 启动日志打印实际路径；测试里断言 `os.path.exists(db)` |
| WAL | 用 `PRAGMA journal_mode=WAL` 读回到 `wal` 才算生效 | 用 `ExecuteScalar` 读回值，不靠「执行没报错」（PRAGMA 返回结果集，`Execute` 会抛） |
| 表数与索引数 | 启动期自检「声称 vs 实际」（R14） | 打印 `SELECT COUNT(*) FROM sqlite_master WHERE type='table'` 与期望值比对 |
| 软删除 | `deleted ∈ {0,1,2}`，`2` 不进任何查询 | 每条查询都带 `deleted != 2`；有测试断言 |

### 2 · 建串行写链（本阶段最关键，3 小时）

所有影响持久状态的写**必须**进一条串行链，并暴露可 await 的完成信号（R2）。核心结构（语言无关的伪码）：

```
pending = completed()
enqueue(save):
    pending = pending.then(save)      # 后发的写不早于先发的写
PendingSave => pending                # 外部/关窗前/测试可 await
```

四条硬规则：

| 规则 | 为什么 | 怎么验 |
|---|---|---|
| 只有 `enqueue` 一个写入口 | 绕过它 = 回到丢数据老路 | `grep -n "fire and forget"` 类似特征零命中；写操作全走 `enqueue` |
| 防抖/定时器触发的写也必须进链 | 否则 `PendingSave` 是假的 | 防抖回调里改成 `enqueue(flush)` |
| 每个写自己 catch，异常不中断后续写 | 一次失败不该拖死整条链 | catch 里写结构化 `SaveStatus`，且**留脱敏日志**（R13） |
| 对外暴露完成信号 | 否则没人能保证落盘 | 存在 `PendingSave`（或等价物）且被关窗逻辑与测试 await |

### 3 · 关窗冲刷 + 结构化结果（2 小时，R3）

同步的关闭事件不能 `await`，正确姿势三步：

```
关闭事件触发
  → 如果已经在冲刷：放行真正关闭（防递归）
  → 否则：取消本次关闭 → 异步冲刷 → 冲刷完成后主动关闭
冲刷 = 停防抖 + 把待写项排进链 + await 整条链
冲刷返回结构化结果：{status: flushed|failed|partial, pending: N, failed: M, errors: [...]}
```

**关键判据：冲刷结果必须是结构化的，不许是布尔值。**

| 不合格 | 合格 |
|---|---|
| `Flush() -> bool` | `{status:"flushed", pending:0, failed:0}` |
| 冲刷失败后静默退出 | 冲刷失败 → 提示「有 N 项未保存」+ 提供重试/取消退出（不许自动丢弃草稿） |

### 4 · 故障注入（1.5 小时，最容易跳过）

必须**主动制造**四种故障并验证行为：

| 故障 | 怎么造 | 期望行为 | 断言 |
|---|---|---|---|
| 磁盘只读 | `chmod -w` 数据库目录 | 显示「保存失败」结构化结果；草稿保留在输入框 | 输入框内容未丢；无「已保存」字样 |
| 磁盘满 | 用小容量 tmpfs / 造大文件占满 | 同上，且不崩溃 | 进程存活；有脱敏日志 |
| 数据库损坏 | 往 db 文件中间写垃圾字节 | 启动时不崩溃；有明确提示；可恢复（从备份） | 有错误页/对话框；备份恢复可读 |
| 进程被强杀 | 写入后立即 `SIGKILL` 进程 | 已提交的写在重开后仍在（WAL 保障） | 重开读到写入值 |

故障注入用例落 `TEST/test-plan.md`，标「故障注入」类型。

### 5 · 退出重启验证（30 分钟，每条写操作都要覆盖）

```bash
./app --data-dir /tmp/t1 &        # 启动，改一个字段
kill -9 $!                        # 不冲刷直接强杀
./app --data-dir /tmp/t1 &        # 重开
sqlite3 /tmp/t1/app.db "SELECT dueDate FROM TaskModel WHERE id='<id>'"   # 断言具体值
```

判据：断言的是**具体值**（`2026-10-24`），不是「非空」、不是「能查到对象」、不是截图。

### 6 · 提醒与调度（若范围含提醒，1.5 小时）

五步：① **定时器真的启动**（断言 `timer.IsEnabled == true`，这是「零调用点」的唯一护栏）→ ② 引擎判定用窗口法 `(lastCheck, now]` 并覆盖边界（正好到点/跳过整天/睡眠唤醒）→ ③ 到点弹窗 + 去重（同一任务不弹两次）→ ④ 改日期/删除后重算（`LK-` 行 `verified`，删除后不弹孤儿提醒）→ ⑤ 延后/完成写库后调度状态正确。

**最容易翻车的一条**：引擎逻辑全对、54 个测试全绿，但定时器从未启动。护栏断言定时器启用状态是唯一的解药。

### 7 · 导入导出与备份（1 小时）

A 档最低要求：

三项：**导出**（全库 → JSON/SQL，重导入后逐条比对计数与抽样字段）／**备份**（拷整个数据目录的 db + wal + shm 三件）／**恢复**（替换后启动不报错、数据在）。

WAL 未合并时只拷 `.db` 会丢最近写入——**必须三件一起拷，或先 checkpoint**。

### 8 · 回写实现差异（30 分钟）

`SPEC/ARCHITECTURE.md` 与实际实现必然有差异。逐条回写：

| 差异类型 | 记在哪 | 例子 |
|---|---|---|
| 技术选型变化 | `ARCHITECTURE.md` + `DECISIONS.md` | 「原计划 sqlite-net，实际用裸 SQL」 |
| 接口签名变化 | `TRACEABILITY.csv` + 命令清单 | 「加了一个 `revision` 参数」 |
| 未实现的契约要求 | `STATE.md` 里降级 + `unknowns.csv` | 「睡眠唤醒后的提醒补偿没做」 |

**不许**把差异留在脑子里。它是 S8 写测试的输入。

## 门禁 G7

### 机器判定（`gates/rules/g7.py`）

| # | 检查项 | 期望 | 不通过怎么修 |
|---|---|---|---|
| 1 | 真文件持久化 | 持久化测试与运行期均用磁盘文件；`:memory:` 命中数为 0 | 改测试与初始化代码 |
| 2 | 冲刷结构化结果 | 存在冲刷函数且返回结构化对象（含 success/failed/pending 字段） | 改返回类型，补字段 |
| 3 | 冲刷断言存在 | 测试里有「冲刷结果 status == ok」类断言 | 补断言；不许只断言「函数被调用」 |
| 4 | 故障注入用例存在且通过 | `test-plan.md` 有故障注入类型 ≥4 条，对应结果全 pass | 补用例 |
| 5 | 重启读回断言存在 | 有「关连接重开读到新值」的用例且断言具体值 | 补用例；断言不许写「非空」 |
| 6 | 无等待式同步 | 持久化与其端到端护栏测试内 `await sleep\|Thread.Sleep` 命中数为 0（R1） | 改成 await 完成信号 |
| 7 | 启动期自检 | 启动日志含实际表数/索引数与期望值的比对 | 补自检代码与日志 |
| 8 | catch 不留空 | `catch` 块为空体的命中数为 0（R13） | 至少留脱敏日志 |

## 常见翻车点

| # | 症状 | 真因 | 对策 |
|---|---|---|---|
| 1 | 改完关窗，数据丢了（失效模式 03） | fire-and-forget / 防抖不在写链 / 关窗不冲刷 | 串行链 + 防抖进链 + 关窗三步冲刷；G7 判定 2/3 |
| 2 | 测试全绿，用户一用就崩（失效模式 04） | 用 `sleep` 猜完成、用内存库测持久化 | R1/R4/R5；真文件 + 完成信号 + 故障注入 |
| 3 | 提醒永不触发（零调用点） | 定时器定义了但没接线；测试绕过 | 断言 `timer.IsEnabled`；只走真实控件事件 |
| 4 | PRAGMA 报 `not an error` | `journal_mode` 返回结果集，不能 `Execute` | 一律 `ExecuteScalar` 并读回断言（R14） |
| 5 | 只拷 `.db` 备份，恢复后少了最近几条 | WAL 未 checkpoint，数据还在 `-wal` 文件里 | 三件一起拷，或先 `wal_checkpoint(TRUNCATE)` |
| 6 | 分析时把真实库搞坏（失效模式 07） | 直接对真实库操作 | 默认操作副本；真实库只读；写进 AGENTS.md 第一条 |
| 7 | catch 吞异常，索引没建成也不知道 | 空 catch 或只 `return`（R13） | 至少留脱敏日志 + 启动期自检比对 |
| 8 | 编译过但行为静默错（空壳实现，失效模式 08） | 抄了反编译代码里的空壳方法 | R8/R9：只当规格书；关键路径自己写并测试 |

## 示例

### 示例 1 · 串行写链 + 结构化冲刷（伪码，语言无关）

```
class DetailStore:
    pending = completed()

    def enqueue(save_fn):            # 唯一写入口
        pending = pending.then(save_fn)

    @property
    def PendingSave(self): return pending    # 外部可 await

    def flush(self) -> FlushResult:          # 关窗前调用
        debounce.stop()
        enqueue(pending_text_write)
        await pending
        return FlushResult(status="flushed", pending=0, failed=0, errors=[])

# 关窗
on_closing(e):
    if flushing: return                # 第二次进来放行真关
    e.cancel = True; flushing = True
    r = await flush()
    if r.status == "flushed": close()
    else: show_error(f"有 {r.failed} 项未保存，重试还是直接退出？")
```

`FlushResult` 有三个数值字段，而不是一个布尔——这是 R3 的实质。

### 示例 2 · 退出重启验证的实样

```text
$ ./app --data-dir /tmp/t1 &                       # 启动
$ # 把任务 dueDate 从 2026-10-23 改成 2026-10-24
$ kill -9 $!                                       # 不冲刷直接强杀
$ ./app --data-dir /tmp/t1 &                       # 重开
$ sqlite3 /tmp/t1/app.db "SELECT dueDate FROM TaskModel WHERE id='t-001';"
2026-10-24                                        # 断言具体值 —— 通过
```

注意 `kill -9` 而不是正常退出：正常退出会走冲刷，测不出「已提交的写是否抗强杀」。

### 示例 3 · 故障注入的一段（磁盘只读）

```text
$ chmod -w /tmp/t1
# 改标题 → 期望：输入框内容保留 + 显示「保存失败：磁盘只读」+ 有重试入口
# 断言：input.value == "我改的标题" 且 status_text 含 "保存失败" 且不含 "已保存"
```

「不含『已保存』」这个反向断言很重要：很多实现失败时不清除旧的「已保存」提示，用户以为存上了。

| 交接物 | 门槛 | S8 怎么用 |
