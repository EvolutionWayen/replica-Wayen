# S10 · 痛点与差异化

> 上游：真实用户评价 · 下游：S2 契约补写（不是直接进代码）· 门禁：G10 · 可提前单跑

## 一句话

去读真实用户骂原版什么，每条都要带链接与样本量；然后把「骂得最多的那几条」变成你产品的改进项——但改进项只能走 **S2 契约补写** 进代码，不许直接开工。

## 输入

| 从哪来 | 内容 | 缺了就不许开工 |
|---|---|---|
| 真实评价 | 应用商店/论坛/社交平台/差评区的原始文本 + URL | 只有「听说大家都说贵」这类转述 → 停，无法计数也无法引用 |
| 自己的抱怨 | 你使用原版时真实遇到的不满（A 档可只做这一部分） | A 档允许只有这一源，但必须写清「样本量 = 1（我自己）」 |
| 评分基线 | `REPORT/parity.md`（S9） | 缺 → 不知道改完之后和原版差多少，改进无法验收 |
| 契约 | `contracts/*.md` | 缺 → 改进项无处落地 |

**样本量纪律**（本阶段唯一的硬约束）：每条痛点必须写 `样本量` 与 `来源数`。样本量 <3 或来源 <2 的，标 `thin`（薄弱），不许单独据此做决策。

## 动作序列

### 1 · 采集原始评价（2 小时）

```bash
# 固定列，逐条填，不许概括
printf 'theme,quote,url,source,date,sample_n\n' > REPORT/reviews.csv
```

要点：

| 要求 | 说明 | 反例 |
|---|---|---|
| 一条一 URL | 每条评价指向能打开的具体页面 | 「App Store 评论区」 |
| 原话照抄 | 保留原文语言的原始措辞（含错别字） | 把「太贵了每加一个人就涨价」概括成「价格问题」 |
| 记日期 | 用来判断是否已在新版本修复 | 无日期 |
| 记来源 | App Store / Reddit / 小红书 / 同事 | 无来源 |
| 不编造 | 想不起原话的，删掉这条 | 凭印象写一条 |

**A 档简化路径**：只采「我自己用起来骂的」也合法，但 `reviews.csv` 的 `source` 列全部写 `self`，`sample_n` 写 `1`，并在报告里写明「样本量 1，结论仅代表我自己」。这是诚实，不是缺陷。

### 2 · 主题归并（1 小时）

把评价归到主题，按出现次数排序：

```bash
python3 replica-skill/replica-entrepreneur/reviews.py REPORT/reviews.csv
```

工具会：丢掉没有链接的行；每条引文都从你给的行里抄；<3 条或单一来源的主题标 `thin`。

主题表：

| 主题 | 出现次数 | 来源数 | 典型原话（带链接） | 薄弱? | 能否在本版解决 |
|---|---|---|---|---|---|
| 按人涨价 | 12 | 3 | 「…」（URL） | 否 | 不适用（本版不收费） |
| 无短信提醒 | 9 | 2 | 「…」（URL） | 否 | 否（需短信通道） |
| 时区让人困惑 | 7 | 2 | 「…」（URL） | 否 | 是（本地时区显式标注） |
| 日期误触改错年 | 5 | 1 | 「…」（URL） | **是**（单一来源） | 是（去掉微调箭头 + 撤销） |

### 3 · 转成改进项（90 分钟，本阶段最关键的一步）

改进项**不是功能需求**，是「契约补写申请」。每条写成一个四段块：

```markdown
### IMP-01 · 日期误触后无撤销

| 项 | 内容 |
|---|---|
| 痛点 | 点日期框右侧微调箭头，一秒内把日期改成几年后，且无撤销 |
| 证据 | `REPORT/reviews.csv` 第 14 行（URL）+ 我自己遇到 3 次（sample_n=3, source=2） |
| 改进动作 | ① 删除数值微调控件 ② 日期改动后给 5 秒撤销条 ③ 整块点击弹日历 |
| 落在哪个契约 | `C-F-DATE-EDIT` §9 状态变化 + §14 撤销与恢复 |
| 如何验收 | 点日期框不再出现微调箭头（控件数 = 0）；改动后 5 秒内可撤销；撤销后 dueDate 回到原值 |
| 影响面 | `LK-001..006` 全部；`T-101..105` 全部重跑 |
```

规则：

| 规则 | 为什么 |
|---|---|
| 必须指到具体契约的**具体节** | 否则实现时无处落地，会变成「顺手加的」 |
| 必须有可验收的断言 | R11：不能写成数值或步骤的要求 = 无效要求 |
| 必须列影响面 | 改进项改了行为 → 受影响的联动与测试都要重跑 |
| 不许直接写进 `src/` | 见下一步 |

### 4 · 走契约补写（不是直接改代码）

```
改进项 IMP-xx
  → 决定做不做（产品官）
  → 做：写进 features.csv（original=no，标为差异化功能）
        → 补/改对应契约（走 S3 的变更单流程，蓝图版本 +1）
        → 更新 linkage.csv 六面
        → 起草 T- 用例
        → 才可以进 S6/S7 实现
  → 不做：写进 PROJECT.md 的不做清单（四段式）
```

**这条路径不许抄近道**。00 §2 的 G10 判定原文就是「改进项必须走 S2 契约补写，不许直接进代码」——因为直接进代码的改进项没有契约，没有联动，也没有测试，三周后没人说得清它该是什么行为。

### 5 · 写定位角度（30 分钟，C 档必做，A/B 档可跳）

一句话说明「为什么用你的而不是原版」，格式：

```
给 <谁>，在 <什么场景> 下，<我的产品> 比 <原版> 好在 <具体一件事>，因为 <可验证的差异>。
```

反例：「更好用、更轻、更快」——三个词都不可验证。正例：「给我自己，在下班整理今天任务时，我的版本比目标应用少 3 次点击，因为它把『挪到明天』做成了一个手势。」

### 6 · 跑 G10（10 分钟）

## 细节级产出

| 文件 | 最小内容 | 判定它「够细」的标准 |
|---|---|---|
| `REPORT/reviews.csv` | 列齐：`theme,quote,url,source,date,sample_n` | 每行有可打开的 URL；原话照抄；无编造（抽查 3 条能打开且内容对得上） |
| `REPORT/feedback.md` | 主题表（次数/来源数/原话链接/薄弱标记）+ 改进项块 + 定位角度 | 每条痛点带 URL 与计数；`thin` 项有标记；每条改进项指到契约的具体节 |
| `BLUEPRINT/features.csv` 追加 | 改进项行（`original=no`） | 新增行有 `contract_ref` 与 `acceptance_ref`；`progress=no`（还没做） |
| `BLUEPRINT/CHANGES/C-xxx.md` | 每条做了的改进项一个变更单 | 影响面列具体 ID；有产品官确认 |
| `PROJECT.md` 不做清单追加 | 决定不做的痛点 | 四段式齐（不做/因为/替代/重议） |

## 门禁 G10

### 机器判定（`gates/rules/g10.py`）

| # | 检查项 | 期望 | 不通过怎么修 |
|---|---|---|---|
| 1 | `feedback.md` 存在 | 含主题表 + 改进项块 | 按结构补齐 |
| 2 | 每条痛点带 URL | `reviews.csv` 与 `feedback.md` 里每条都有非空 URL | 补链接；找不到链接的条目删掉 |
| 3 | 样本量已声明 | 每个主题有 `出现次数` 与 `来源数` | 补计数；不许写「很多」「普遍」 |
| 4 | 薄弱主题已标记 | 次数 <3 或来源 <2 的标 `thin` | 补标记 |
| 5 | 无编造条目 | 抽查 URL 能打开且引文与页面一致 | 删除无法核实的 |
| 6 | 改进项有契约落点 | 每条改进项写明 `C-F-xxx` 的 §编号 | 补节号；指不到说明还没想清 |
| 7 | 改进项未直接进代码 | 做了的改进项在 `features.csv` 有行，且 `contract_ref` 非 `-` | 补 `features.csv` 行与契约，不许只在代码里出现 |
| 8 | 不做项已记录 | 决定不做的痛点进了 `PROJECT.md` 不做清单 | 补四段式条目 |

### 人工判定（产品官）

| # | 判什么 | 判定问句 |
|---|---|---|
| 1 | 这些痛点是否真是痛点 | 「这条你自己遇到过吗？几次？」 |
| 2 | 改进是否值得做 | 「这个改动会让你更愿意用它吗？」 |
| 3 | 证据是否被夸大 | 「12 条 3 来源，是哪 3 个来源？」 |
| 4 | 是否在替用户编需求 | 「这条改进是真的有人骂，还是你觉得该有？」 |

## 常见翻车点

| # | 症状 | 真因 | 对策 |
|---|---|---|---|
| 1 | 改进项直接进代码，三周后没人说得清它该是什么行为 | 跳过契约补写 | G10 判定 7：做了的改进项必须在 `features.csv` 有行且 `contract_ref` 非 `-` |
| 2 | 痛点写得像营销文案 | 概括掉了原始措辞与链接 | 原话照抄 + URL；工具会丢掉无链接的行 |
| 3 | 用「很多用户抱怨」当证据 | 没有样本量与来源数 | G10 判定 3：两个数都必须填，`thin` 要标 |
| 4 | 改进项没有可验收的断言（R11） | 写成「优化时区体验」 | 每条改进必须有「如何验收」且是数值或步骤 |
| 5 | 改进破坏了原本通过的功能（R10） | 没列影响面、没重跑受影响测试 | 影响面列到 `T-` 号；改完全链路复验 |
| 6 | 把原版的商业问题当成功能缺陷 | 例如「按人涨价」在本版不存在 | 主题表加「能否在本版解决」列，不适用就写出来 |
| 7 | 样本量极小的结论被当成方向 | 单一来源的 5 条被当作主流 | `thin` 标记 + 人工判定 3 追问来源数 |

## 示例

### 示例 1 · reviews.csv 的真实样子（注意原话照抄与 URL）

```csv
theme,quote,url,source,date,sample_n
日期误触,点在日期框右边那个小箭头上日期就被改成 2029 了根本没有撤销,https://example.com/review/12345,App Store,2026-10-20,1
日期误触,改日期太容易点错而且点了就保存了,https://example.com/forum/thread/88,Reddit,2026-10-18,1
日期误触,又一次把任务改到下个月了自己都不知道,self,自用记录,2026-10-22,1
时区困惑,旅行回来所有提醒时间都乱了,https://example.com/review/22341,App Store,2026-10-19,1
```

注意第二行的措辞「点了就保存了」——这才是能推出「需要撤销」的原始证据；如果概括成「交互问题」，什么都推不出来。

### 示例 2 · 一个完整的改进项（含影响面）

```markdown
### IMP-01 · 日期改动后无撤销

| 项 | 内容 |
|---|---|
| 痛点 | 日期一改就落库，误触后无法恢复 |
| 证据 | `reviews.csv` 3 条（2 个来源 + 我自己）+ `ux-04-date-misclick.png` |
| 改进动作 | ① 去掉数值微调控件 ② 改动后显示 5 秒撤销条 ③ 撤销后恢复到改动前值 |
| 落在哪个契约 | `C-F-DATE-EDIT` §9（状态变化加「可撤销」分支）+ §14（撤销与恢复：窗口期 5000ms） |
| 如何验收 | ① 日期框内微调控件数 == 0 ② 改动后 5 秒内出现撤销条 ③ 点撤销后 `dueDate` == 原值 ④ 6 秒后撤销条消失且改动保留 |
| 影响面 | `LK-001..006`（六面联动不变，但撤销要重新触发一遍）；`T-101..105` 全部重跑；新增 `T-106`（撤销） |
```

「6 秒后撤销条消失且改动保留」这一条是很多人漏掉的边界——撤销窗口过期后的行为也必须定。

### 示例 3 · A 档的诚实写法

```markdown
（feedback.md 的「## 样本量声明」小节正文）

本报告样本量 = 1（我自己，2026-10-20 ~ 10-22 使用记录），来源数 = 1。
下表 6 条痛点全部来自我自己的使用，不代表任何其他用户。
结论适用范围：仅用于我自己的版本取舍，不得用于任何对外宣称。
```

A 档做 S10 完全合法，但不许把「我自己觉得」写成「用户反映」。

## 退出与交接

| 交接物 | 门槛 | 下游怎么用 |
|---|---|---|
| `REPORT/feedback.md` | 主题表 + 改进项 + 样本量声明 | 改进项决定后进 `features.csv` |
| `REPORT/reviews.csv` | 每条有 URL 与来源 | 抽样可核实 |
| `features.csv` 追加行 | `original=no` + 契约引用 | S6 按 `WP-` 排队实现 |
| `BLUEPRINT/CHANGES/` | 每条做了的改进项一单 | 蓝图版本 +1，重算哈希 |
| `PROJECT.md` 不做清单 | 决定不做的痛点四段式 | 防止三周后被重新提出 |

**交接状态要求**：G10 退出码 `0`；每条痛点带 URL 与计数；改进项全部走契约补写，无一条直接进代码。

**下一个接手的人需要知道的唯一一句话**：这里的每条结论都能指到一个能打开的链接和它的样本量；指不到的已经删了。
